# 시각화·리포트 — 사업 결정과 근거 (2026-08-02)

`ontology-studio-strategy.md` §5·§6 이 방향을 정했고, 이 문서는 그 방향을 **코드에서 확인한
사실 위에 올려 결정으로 굳힌 것**이다. 명세 전문이 아니라 **무엇을 정했고 왜 그렇게 정했는지**만
담는다. 요구사항·규칙표·수용 기준은
[`specs/006-visualization-and-report/spec.md`](../../specs/006-visualization-and-report/spec.md) 에 있다.

이 문서는 향후 `biz-kit` 스킬의 자산이 된다 — 투자·영업·데모 자료에서 재사용할 수 있는 형태로
남기는 것이 목적이다.

---

## 1. 왜 이것이 지금 1순위인가

전략 §1 대조표가 사업안의 전제를 세 덩어리로 나눴다. 그 중 **코드가 정확히 0인 항목은 시각화·
리포트 하나뿐**이다. 다시 확인했고 여전히 사실이다:

- 프론트 의존성은 `cytoscape`(그래프 전용) · `marked` · `vue` 셋뿐 — `frontend/package.json:11-15`.
  `echarts`/`chart.js` 는 잠금파일의 전이 의존성까지 뒤져도 **0건**
- 백엔드에 PDF 생성기도, 마크다운 변환기도, 템플릿 엔진도 없다 — `pyproject.toml:10-31`
- 채팅 화면에 **표를 그리는 코드조차 없다.** 표가 보인다면 그건 LLM 이 답변 텍스트에 마크다운
  표를 직접 타이핑한 것이다 — `ChatPanel.vue:111-114, 141-143`

그래서 순서를 **시각화 → 데스크톱 패키징**으로 잡았다. 뒤집으면 *"SQL 결과를 표로 보는 도구"*
라는 PoC 인상을 굳힌 채로 배포하게 된다. 전략 §4-3 의 카피 — *"AI가 우리 회사 DB를 정확히
이해하게 만든다 — 질문하면 차트와 리포트까지"* — 도 이 기능 하나에 걸려 있다.

## 2. 무엇을 만들기로 했는가

파이프라인은 전략 §5 가 정한 그대로다.

```
[자연어 질의] → [Text-to-SQL / behavior_invoke]  ← 기존, 구현됨
              → [차트 추천 (결정적)]              ← 신규
              → [ECharts 렌더]                    ← 신규
              → [리포트 조립 + LLM 인사이트]      ← 신규
              → MD / HTML / PDF
```

이번 조사로 **여기에 세 가지 결정이 더해졌다.**

### 결정 1 — 차트는 자동으로, 리포트는 에이전트가 요청받아서

두 산출물의 성격이 다르다.

- **차트는 결과의 성질이다.** "이 결과는 시계열이다"는 사용자가 원하든 말든 참이다. 물어볼 것이
  없으므로 **자동**이 옳다. 에이전트에게 맡기면 호출을 잊는 순간 차트가 사라진다 — 매 질의마다
  신뢰할 수 없는 기능이 된다.
- **리포트는 사용자의 의도다.** 어떤 결과들을 묶을지, 어떤 순서로 놓을지는 결과에서 도출되지
  않고 대화 맥락에만 있다. 그래서 **에이전트 도구**로 만든다.

### 결정 2 — 차트 계산은 백엔드 도구 계층에서 한다 (에이전트도 프론트도 아니다)

이건 취향 문제가 아니라 **데이터가 어디에 있는지의 문제**였다. 조사에서 나온 사실:

| 위치 | 볼 수 있는 행 수 | 근거 |
|---|---|---|
| 에이전트 | **30행** | `DATASOURCE_AGENT_ROW_PREVIEW` 기본 30 — `settings.py:192` |
| 프론트엔드 | **0행** | 진행 상황 이벤트가 스칼라만 싣는다 — `service.py:923` *"never rows, never SQL"* |
| 백엔드 도구 함수 내부 | **전체 (최대 500)** | `tools.py:1645` 의 잘라내기 직전 |

**500행짜리 시계열을 에이전트가 그리면 30점짜리 그래프가 된다.** 그리고 그건 조용히 틀린다 —
사용자는 그게 잘린 그래프인 줄 모른다. 유일하게 전체 데이터가 있는 곳에서 계산해야 한다.

부수 효과로 이 위치는 **두 에이전트 백엔드(내장 deepagents / 외부 CLI)에 자동 반영**된다.
MCP 브리지가 같은 함수 객체를 그대로 등록하기 때문이다 (`agent_bridge_mcp/server.py:44-45`).
한 번 만들면 양쪽이 같이 얻는다.

### 결정 3 — PDF 에 새 의존성을 넣지 않는다. 브라우저가 인쇄한다

선택지를 다 놓고 봤을 때, **백엔드에 무언가를 더 넣는 모든 선택지가 전략 §4-1 과 충돌했다.**
실측 idle 이 이미 5.36 GiB 이고 권장 사양을 16GB 로 올린 상황에서, 백엔드 이미지에 Chromium
(수백 MB)이나 WeasyPrint(cairo/pango 시스템 라이브러리 + CJK 폰트)를 더하는 것은 앞뒤가 맞지 않는다.

채택한 경로:

- **MD 가 정본** — 백엔드가 의존성 0으로 만든다
- **HTML** — 프론트가 렌더하고, 차트는 ECharts 가 **SVG 로 구워 인라인**한다 (결과 문서에
  자바스크립트 0)
- **PDF** — 그 HTML 을 브라우저가 인쇄한다. Electron 이 오면 `printToPDF()` 로 자연스럽게 승계된다

전략 §5 가 이미 같은 말을 적었다 — *"PDF 생성은 이미 Electron/Chromium이 있는 환경에서는 별도
엔진이 필요 없다."* 조사 결과는 그 판단을 뒷받침했다.

**부수적으로 확인한 것**: README 의 "LibreOffice 설치 때문에 첫 빌드가 오래 걸린다"는 서술은
사실이지만 설치되는 것은 **`libreoffice-calc` 하나**다(`backend/Dockerfile:9`). 게다가 그
설치의 원래 소비자였던 파일(`recalc.py`)은 저장소에 없고, `soffice` 를 호출하는 코드도 **0건**
이다. **PDF 수단으로 계산에 넣지 않는다.**

### 결정 4 — 리포트 export 는 기존 파일 경로를 그대로 쓴다

에이전트가 출력 디렉터리에 파일을 쓰면 **이미 3중 경로로** 프론트에 노출된다: 도구 결과에서
경로를 긁고(`service.py:1054-1059`), 턴 종료 시 디렉터리를 스캔해 `done` 이벤트에 싣고
(`service.py:1737, 1830-1838`), `GET /api/files` 폴링이 목록을 갱신한다.

**즉 리포트 파일을 출력 디렉터리에 쓰기만 하면 다운로드 버튼이 UI 코드 변경 0줄로 생긴다.**
새 엔드포인트를 만들지 않는다. (HTML 을 브라우저에서 *열리게* 하려면 `media_type` 한 줄만
고치면 된다 — `files/api.py:49`.)

## 3. 차트 타입은 LLM 이 고르지 않는다 — 이유

전략 §5 의 확정 사항이고, 조사가 이유를 하나 더 보탰다.

원래 이유 세 가지:
1. 플랫폼 계약이 **테이블→온톨로지 경로에 이미 같은 원칙**을 적용 중이다 — 같은 카탈로그는 항상
   같은 온톨로지를 만든다.
2. 컬럼 타입·카디널리티·시계열 여부만으로 결정 가능한 문제에 LLM 을 부르면 비결정성·지연·비용만
   는다.
3. LLM 은 차트 **선택**이 아니라 인사이트 **문장**에 쓴다.

조사가 더한 네 번째 이유: **LLM 은 애초에 판단할 데이터가 없다.** 30행만 본다. 카디널리티도
행 수도 값 범위도 틀리게 판단한다.

그리고 판정에 필요한 재료가 **이미 저장소에 있다**는 것도 확인했다 — SQL 타입 → 온톨로지 타입
매핑(`schema_ontology.py:51-66`), 식별자 접미사 목록(`:40`), 바인딩의 컬럼 타입 맵(`:270-279`),
카탈로그 정규화 지점(`datafabric_client.py:133-160`). **새로 발명할 것이 아니라 연결하면 된다.**

규칙표는 spec.md 의 §차트 추천 규칙에 있다. 원칙 두 개만 여기 남긴다:

- **폴백이 항상 있다.** 어떤 규칙에도 걸리지 않으면 표를 보여준다. **차트를 억지로 그리지 않는다.**
- **차트는 재집계하지 않는다.** 집계는 SQL 의 일이다. 그래야 화면의 숫자와 답변의 숫자가 어긋나지
  않는다.

## 4. OSS 로 주는 것 / Enterprise 로 남기는 것

전략 §3 의 경계표를 그대로 따른다. 원칙: **1인 1머신에서 완결되는 것은 전부 무료. 여러 사람·
여러 머신을 엮는 순간 유료.**

| | OSS (무료) | Enterprise (유료) |
|---|---|---|
| 차트 | ECharts 로컬 렌더링, **세션 한정** | 대시보드 **저장·공유** |
| 리포트 | **수동 1회** export (MD/HTML/PDF) | **정기 생성·배포**(메일/슬랙), 템플릿 관리 |
| BI | 없음 | Superset/Metabase 커넥터, 온톨로지→Dataset 동기화 |
| 접근 제어 | 없음 (로컬) | 리포트 권한·감사 로그 |

이 선이 잘 그어지는 이유: **저장하는 순간 "누가 볼 수 있는가"가 생기고, 그건 권한 문제다.**
세션 한정 차트에는 그 질문이 없다. 스케줄 리포트도 마찬가지로 상주 서버를 요구한다. 우회가
성립하지 않는 선이다.

**Superset 은 로컬에 넣지 않는다.** Flask+Redis+Celery+Postgres 의존성이 *"설치 없이 로컬 실행"*
이라는 가치 제안과 정면 충돌한다. 전략 §5 의 판단을 유지한다.

## 5. 이 기능이 여는 것 — 고객 세그먼트와 데모

### 세그먼트

전략 §2 가 표시한 대로, 시각화·리포트는 **세 번째 세그먼트인 현업 비즈니스 사용자**를 여는
조건이다. 현재 두 세그먼트는 데이터 엔지니어·AI 개발자(커뮤니티)와 보안 민감 산업의 IT/DX
부서(엔터프라이즈)다.

현업 사용자의 판단 기준은 개발자와 다르다:

| | 개발자·분석가 | 현업 비즈니스 사용자 |
|---|---|---|
| 성공의 모습 | 정확한 SQL 이 나온다 | **회의에 들고 갈 문서가 나온다** |
| 결과 형태 | JSON·표로 충분 | 차트·PDF 가 아니면 쓸 수 없다 |
| 도구 평가 | MCP 연동, 환각 억제 | "질문하면 답이 그림으로 나오는가" |

**현업 사용자는 JSON 을 읽지 않는다.** 지금 제품이 주는 것은 마크다운 텍스트뿐이므로, 이
세그먼트는 아직 열려 있지 않다.

### 데모 시나리오 후보

전략 §6 의 영상 증거 규칙과 같은 자산을 쓴다 (`ontology-studio/demo/` 의 Playwright 파이프라인).
영업·투자 자료에 그대로 쓸 수 있는 순서로:

1. **"질문 하나 → 차트 하나"** (30초) — 설비별 불량률 추이를 묻고, 답변과 함께 선 그래프가
   **아무 조작 없이** 뜬다. 가장 짧고 가장 강한 장면이다.
2. **"결정적이다"** (20초) — 같은 질문을 두 번 던져 **차트가 동일함**을 보인다. 경쟁 제품의
   "LLM 이 그려주는 차트"와 갈라지는 지점이고, 기업 고객이 실제로 묻는 질문이다.
3. **"정직하다"** (20초) — 규칙에 걸리지 않는 결과에서 **차트를 그리지 않고 표만** 보여준다.
   잘린 결과에서는 **"상위 N건만" 배지**가 뜬다. *억지로 그리지 않는다*는 것이 신뢰의 근거다.
4. **"회의 자료가 나온다"** (40초) — 두세 개 질문 후 "리포트로 만들어줘" → 다운로드 → PDF 를
   여는 장면. **현업 세그먼트를 향한 핵심 장면.**
5. **"클라우드로 아무것도 안 나간다"** (20초) — 네트워크를 끊은 상태에서 1~4 가 그대로 동작한다.
   전략 §4-1 이 정한 진짜 차별점(*"경량성이 아니라 로컬 완결성과 데이터 비유출"*)의 시연이다.

**규칙**: 전략 §6 대로, 되지 않는 부분은 숨기지 말고 **그대로 녹화하고** 무엇이 안 되는지 적는다.
증거는 개발자용 로그가 아니라 **화면 그 자체**여야 한다.

## 6. 구현 난이도와 의존성

| 작업 | 난이도 | 의존성 | 비고 |
|---|---|---|---|
| **선행: 잘림 신호 수정** | 낮음 | 없음 | 실행 서비스가 이미 정확한 값을 주는데 읽지 않고 있다. **읽기만 하면 된다** |
| 결과 정규화 + 결과 저장소 | 중간 | 선행 | 도구 4종의 서로 다른 결과 형태를 하나로 모은다 |
| 컬럼 타입 판정 | **낮음** | 결과 정규화 | 매핑·접미사 목록이 **이미 있다.** 연결 작업 |
| 차트 추천 규칙 엔진 | 중간 | 타입 판정 | 순수 함수. **단위 테스트로 전부 검증 가능** |
| ECharts 도입 + 렌더 컴포넌트 | 중간 | 없음 (병렬 가능) | 신규 프론트 의존성 1개 |
| SSE 이벤트 1개 추가 | 낮음 | 규칙 엔진 | 기존 이벤트는 손대지 않는다 |
| 리포트 생성 도구 | 중간 | 결과 저장소 | 답변 스킬 `SKILL.md` 수정 동반 |
| HTML/PDF export | 중간 | 리포트 + ECharts | **백엔드 의존성 0** |

**병목은 기술이 아니라 선행 수정이다.** 잘림 신호가 틀린 채로 차트를 붙이면 틀린 그래프가 틀린
줄 모르고 나간다.

### 신규 의존성 총계

- 프론트: **ECharts 1개**
- 백엔드: **0개** ← 이 설계의 핵심 성과

## 7. 리스크

| # | 리스크 | 왜 중요한가 | 대응 |
|---|---|---|---|
| **R-1** | **잘림 신호가 틀린 채로 차트가 나간다** | 사업 자료에 틀린 그래프가 실린다. 신뢰는 한 번 잃으면 회복이 어렵다 | 잘림 수정을 **선행 조건**으로 못박았다. 미해결 상태로 완료 처리하지 않는다 |
| **R-2** | 자동 차트가 원치 않는 상황에도 뜬다 | 소음이 되면 기능이 꺼진다 | 폴백 규칙(안 걸리면 표)이 대부분 흡수. 잦으면 스위치 추가 |
| **R-3** | 타입 추론이 빗나가 이상한 차트 | 자연어 폴백의 파생 컬럼(`COUNT(*)` 등)에서 잦을 것 | 타입 출처 기록 + 규칙 근거 표시 + 수동 변경 |
| **R-4** | PDF 결과가 브라우저마다 다르다 | 여백·페이지 나눔 | 인쇄 전용 스타일시트. Electron 이 오면 Chromium 하나로 고정 |
| **R-5** | 단독 스킬 사용자(spec 005)는 차트를 못 본다 | *"스튜디오 없이 쓴다"*는 약속과 어긋나 보인다 | 스킬 본문이 차이를 명시. MD 리포트는 동일하게 나온다 |
| **R-6** | 이미지 빌드가 무관한 이유로 깨져 **영상 증거를 못 만든다** | `backend/Dockerfile:33` 이 존재하지 않는 `backend/skills/` 를 `cp -r` 한다 | 이 기능과 무관하나 **선행 확인 항목**. 실제 빌드 실패 여부는 미확인 |

### 사업 판단이 필요한 미결 항목

- **answer 모드가 리포트 파일을 쓰는 것이 플랫폼 계약에 걸리는가.** 현행 문구는 *"answer 에는
  쓰기 도구를 올리지 않는다"* 이고 의도는 그래프·데이터 쓰기 금지로 읽히지만, 문구상으로는
  걸린다. Governance 규칙(*"위반이 필요하다면 먼저 이 문서를 고친다"*)대로 **구현 전에 계약을
  개정**할지, 리포트를 별도 경로로 뺄지 정해야 한다.
- **ECharts 번들 크기.** 로컬 완결성 때문에 CDN 은 불가하다. 전체 번들과 tree-shaking 중 무엇을
  쓸지는 실측 후 정한다.

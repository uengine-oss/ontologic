# text2sql·분석기를 스킬 기반으로 — 사업 결정과 근거

**작성일** 2026-08-03 · **대상** `neo4j-text2sql` (제자리 리팩터링) · 메타데이터 증강 분석기 (교체)

**전제 문서** [`agent-backend-and-llm-access.md`](agent-backend-and-llm-access.md) —
이 문서가 결정한 *"`cliagents` 에서는 text2sql·ingestion 을 스킬로 돌린다"* 의 실행 판단이다.

에 있다. 여기에는 **결정·비용·리스크·단계**만 적는다.

이 문서의 사실 주장에는 `파일:줄` 또는 실측 출처가 붙어 있다. 확인하지 못한 것은
§「확인하지 못한 것」에 모았다. 추정치는 그렇게 표시했다.

## 1. 왜 지금인가 — 같은 날 같은 이유로 두 서비스가 멈췄다

`agent-backend-and-llm-access.md` 는 2026-08-02 에 결정을 내리고 하루 뒤 구현 현황을 갱신하며
이렇게 적었다:

> **text2sql 은 여전히 자기 몫의 LLM·임베딩을 직접 부른다.** … 첫 실행 경험은 "선택 화면 → 앱
> 진입" 까지 깨지지 않지만, **데이터소스 자연어 질의는 여전히 비활성**이다.

같은 날 [`evidence/11-analysis-pipeline/README.md`](evidence/11-analysis-pipeline/README.md) 는
분석 파이프라인이 3단계 `scan_codebase` 에서 `invalid_api_key` 로 멈췄고 4~7단계와 임베딩·요약에
도달하지 못했다고 기록했다.

**두 서비스가 같은 이유로 같은 날 멈췄다.** 제품 관점에서 이것은 하나의 결함이다 —
*"다운로드 한 번으로 로컬에서 돈다"* 가 데이터 질의와 메타데이터 증강 **양쪽에서** 성립하지 않는다.
그래서 두 리팩터링을 한 스펙으로 묶었다.

## 2. 결정 1·2 — 색인 단계가 통째로 없다. 그것이 진짜 결함이다

### 확인한 사실 — 진단이 한 단계 얕았다

초판은 이것을 "text2sql 이 임베딩을 OpenAI 에 고정한 문제"로 봤다. 다시 조사해 보니
**누가 벡터를 채우는가**가 진짜 질문이었고, 답은 **"아무도"** 였다.

| 사실 | 확인 경로 |
|---|---|
| **`data-fabric/backend/app` 전체에 임베딩 코드가 0건** | `grep -rniE "embedding\|embed_text\|embed_batch" data-fabric/backend/app --include="*.py"` → **0** |
| ReAct 인덱스는 **text2sql 부팅 잡**이 채운다 (블로킹) | `app/core/text2sql_table_vectorizer.py:270` ← `app/main.py:72` |
| 레거시 두 인덱스는 **사람이 설명을 손으로 고칠 때만** 채워진다 | `app/routers/schema_edit.py:111`(테이블) · `:194`(컬럼) |
| 질의 시점에는 임베딩이 **반드시** 필요하다 (질문을 벡터로) | `app/routers/ask.py:115` · `app/routers/watch_agent.py:81` |
| **코드가 이 결핍을 이미 알고 있다** — 비어 있는 것을 정상 상태로 취급 | `app/core/text2sql_runtime_repair.py:58,124-136` — *"Every table misses text_to_sql_embedding_text"* |
| 임베딩 클라이언트는 `base_url` 을 받지 않는다 | `app/core/llm_factory.py:116-118` |
| `EMBEDDING_PROVIDER` 가 `openai` 가 아니면 `NotImplementedError` | `app/core/embedding.py:13-17` |
| 벡터 어디에도 **무슨 모델로 만들었는지 기록이 없다** | `text2sql_table_vectorizer.py:270-273` |

즉 **색인이 추출 파이프라인의 단계가 아니라 질의 서비스 부팅의 부수효과**로 존재한다.
그 배치 하나가 네 가지 증상을 동시에 낳는다 — 키 없이 기동 실패 / 긴 콜드스타트 /
새 데이터소스에 벡터 없음 / 레거시 인덱스 영구 공백.

두 번째로 아픈 사실: *"데이터가 이 PC 를 떠나지 않는다"* 는 주장이 **임베딩 경로에서 이미
깨져 있다.** 로컬 LLM 을 붙인 고객도 질문 텍스트와 테이블 프로필이 OpenAI 로 나간다.

### 결정

1. **임베딩은 데이터소스 질의의 필수 선행 조건이다.** 없으면 답을 만들지 않고 **거부**한다.
2. **색인을 「메타데이터 증강」 단계로 옮긴다.** 추출이 곧 색인이다.
3. **text2sql 기동은 색인과 분리한다.** 뜨는 것과 질의가 되는 것은 다른 문제다.

이 셋 모두 **컨트롤러를 한 줄도 건드리지 않는다.**

### 왜 `none` 을 "저하 모드"로 두지 않는가 — 초판을 뒤집은 이유

초판은 다축 검색 구조(regex·intent·FK·유사쿼리 축이 남는다)를 근거로 `none` 을 정상 저하
모드로 두려 했다. 두 가지가 그 판단을 무너뜨린다.

- **hyde 축 가중치가 가장 높다**(기본 1.0). 가장 강한 신호를 뺀 나머지를 "약간 나쁨"이라
  부를 근거가 없다.
- **regex 축은 이름이 맞아떨어질 때만 작동한다.** constitution 이 이미 같은 사실을 다른 맥락에서
  기록했다 — *"문서가 한글 도메인 용어를 쓰고 컬럼은 영문 약어이면 이름 유사도가 **0** 이며,
  그것이 정상이다."* **국내 고객의 레거시 스키마가 정확히 그 모양이다.**

그리고 사업적으로 더 중요한 이유가 있다:

> **나쁜 답은 사용자가 검증할 수 없다. 거부는 검증할 필요가 없다.**

Text-to-SQL 제품에서 조용히 틀린 SQL 은 기능이 아니라 **부채**다. 고객이 그 답으로 의사결정을
하면 우리가 책임진다. 거부하면 고객은 무엇을 해야 하는지 알고, 우리는 신뢰를 잃지 않는다.

### 상태를 넷으로 나눈다

| 상태 | 되는 것 | 안 되는 것 |
|---|---|---|
| `indexed` | 전부 | — |
| `indexing` | 온톨로지 설계·그래프 조회 (질의는 진행률과 함께) | 완전한 질의 |
| `stale` (모델 바뀜) | 온톨로지 설계·그래프 조회 | **질의 — 거부.** 낡은 벡터로 답하지 않는다 |
| `unindexed` | 온톨로지 설계·그래프 조회 | **질의 — 거부 + 안내** |

데스크톱이 이미 비슷한 일을 하고 있다 — *"데이터소스 자연어 질의 비활성 — 온톨로지 설계와
그래프 조회는 사용 가능"* (`agent-backend-and-llm-access.md` §임시 조치).
**그 문구를 임시 조치에서 정식 상태 표시로 승격한다.** 다만 이제는 "무엇을 하면 켜지는지"
(= 메타데이터 증강 실행)를 함께 말한다.

### 감수하는 대가 (숨기지 않는다)

**"LLM 키 없이 설치하면 바로 질문할 수 있습니다" 를 쓸 수 없다.** 초판이 이 카피를
사업 가치의 절반으로 제시했으나 근거가 없었다.

정확한 카피는 §3 에 적었다. 약속이 줄었지만 **줄어든 약속이 참이다.**

## 2b. 결정 3 — 임베딩 설정은 필요해지는 순간에 묻는다

### 결정

메타데이터 추출을 시작하는 순간 묻는다. **이미 설정돼 있으면 묻지 않는다.**
설정은 **앱 전역 한 벌**이고 데이터소스마다 다르게 두지 않는다.

### 왜 그 시점인가

선례가 동작하는 형태로 있다 — 첫 실행 에이전트 선택 화면. 그 결정의 근거가 그대로 적용된다:
*"설정 파일을 손으로 여는 일이 더는 필요 없다"*, *"컨테이너 기동(첫 실행 수 분)보다 먼저 묻는다.
순서를 뒤집으면 사용자는 수 분을 기다린 뒤에야 질문을 받는다."*

**다만 시점이 다르다.** 에이전트 선택은 부팅 전이지만, 임베딩은 **추출을 시작할 때**다.
부팅 전으로 당기면 데이터소스를 아직 등록하지도 않은 사용자에게 의미 없는 질문을 하게 된다.
그리고 그 시점이 **비용이 처음 발생하는 시점**이라, 선택지의 대가를 실감하고 고를 수 있다.

### 세 선택지와 각각의 대가 (화면에 그대로 보인다)

| 선택지 | 대가 |
|---|---|
| **제공 LLM 엔드포인트 재사용** | 그 엔드포인트가 임베딩을 서빙해야 한다 |
| **OpenAI** | 키 필요. **데이터가 나간다** |
| **로컬 번들 모델** | **~400 MB 메모리** |

### 왜 데이터소스별이 아니라 전역인가

기술적 이유가 사업적 이유보다 강하다 — §4 참조. 데이터소스마다 다른 모델을 쓰면
같은 그래프의 같은 인덱스에 서로 다른 공간의 벡터가 섞인다. **아무 오류 없이 검색이
무의미해진다.** 전역 한 벌이 이것을 구조적으로 막는다.

## 3. 결정 4 — 임베딩은 스킬로 옮기지 않는다 (초판에서 유일하게 살아남은 결정)

`agent-backend-and-llm-access.md` 가 *"이 리팩토링의 가장 어려운 지점"* 이라고 적은 항목이다.
조사 결과 **어렵지 않다. 불가능하다.**

CLI 에이전트(Claude Code·Codex)는 임베딩 도구를 노출하지 않는다. 004 가 확인한 것과 같은 종류의
한계다 — 004 는 `AskUserQuestion` 이 헤드리스에서 제공되지 않는다는 것을 실측했고, 임베딩은 그보다
더 확실하다(애초에 텍스트 생성 인터페이스다).

**이 결정은 사업 판단이 바뀌어도 바뀌지 않는다.** 임베딩은 결정론 도구로 남는다.

### 사업 관점의 정직한 결론 — 카피를 고친다

`agent-backend-and-llm-access.md` 의 표는 *"`cliagents` → 사용자가 입력할 것: **아무것도**"* 라고
적었다. 이 리팩터링 후에도 그것은 **조건부로만** 참이다:

- 에이전트 대화 · SQL 생성 · 코드 의미 분석 → **참.** CLI 가 자기 모델을 들고 온다.
- **데이터소스 자연어 질의** → **임베딩을 한 번은 골라야 한다.** 어떤 선택지든 "아무것도"는 아니다.

| 쓸 수 없는 카피 | 쓸 수 있는 카피 |
|---|---|
| ~~"LLM 키 없이 설치하면 바로 질문할 수 있습니다"~~ (초판) | **"LLM 키 없이 설치합니다. 데이터를 연결할 때 임베딩 방식만 한 번 고르면 — 로컬 모델을 쓰면 데이터가 PC 를 떠나지 않습니다."** |
| ~~"임베딩이 없어도 동작합니다"~~ | **"색인이 없으면 답을 지어내지 않고, 무엇을 하면 되는지 알려 줍니다."** |

두 번째 줄이 실제로는 **강점**이다. 경쟁 제품이 조용히 틀린 SQL 을 내는 영역에서
"모르면 모른다고 한다"는 엔터프라이즈 구매자가 값을 매기는 성질이다.

## 4. 결정 5 — 로컬 임베딩의 1순위는 **사용자가 이미 돌리는 엔드포인트**다

### 초판이 놓친 것

초판은 "로컬 임베딩 = 우리가 400 MB 모델을 들고 돈다"로 전제하고, 그 400 MB 를 어디에 둘지만
따졌다. **경로가 하나 더 있다.**

`base_url` 누락(`app/core/llm_factory.py:116-118`)과 openai 전용 제약
(`app/core/embedding.py:13-17`)만 고치면, 사용자가 이미 돌리는 OpenAI 호환 서버
(Ollama · LM Studio · vLLM 등)를 임베딩에도 쓸 수 있다.

> **우리 스택 메모리 증가 0 으로 "데이터가 PC 를 떠나지 않는다"가 성립한다.**

*(미확인: 이 환경에서 실제 로컬 서버로 임베딩 왕복을 검증하지 않았다. §12 참조.
이 전제가 틀리면 400 MB 번들 모델이 1순위로 올라온다.)*

### 결정 — 세 선택지의 우선순위

| 순위 | 선택지 | 우리 스택 비용 | 언제 |
|---|---|---|---|
| 1 | **제공 LLM 엔드포인트 재사용** | **0** | 이미 로컬 LLM 을 돌리는 고객 (= 우리의 표적 고객) |
| 2 | **OpenAI** | 0 | 키가 있고 외부 전송이 괜찮은 고객 |
| 3 | **번들 로컬 모델** | **~400 MB** | 아무 엔드포인트도 없는 고객 |

3번만 우리가 모델을 호스트하고, 그 호스트는 **이미 그 스택을 가진 신규 분석기**로 둔다
([`memory-footprint-measurement.md`](memory-footprint-measurement.md) §10-2 실측:
`sentence-transformers` 로 401.4 MiB, `.venv` 932 MB, 비용은 **import 시점**).
두 벌 로드하면 core 3,261.8 MB 에 **+800 MB, +24.5%** 다.

### 한 벌만 두는 진짜 이유는 메모리가 아니다

초판은 이것을 메모리 논거로만 세웠다. 더 강한 논거가 있다:

> **추출이 모델 A 로 색인하고 질의가 모델 B 로 임베딩하면, 아무 오류 없이 코사인 유사도가
> 무의미한 값을 낸다.** 차원까지 같으면 인덱스 검사로도 안 잡힌다.

임베딩 엔드포인트를 하나로 두면 이 불일치가 **구조적으로 불가능**해진다.
그래서 설정도 앱 전역 한 벌이다(결정 3).

### 감수하는 대가

임베딩 엔드포인트가 죽으면 색인과 질의가 함께 멈춘다.
→ 상태가 `indexing`/`stale` 로 표시되고 데이터소스 질의는 거부된다.
**조용히 낡은 벡터로 답하지 않는다** — 초판은 여기서 "`none` 으로 강등해 답한다"고 했고,
그것이 뒤집힌 부분이다.

## 4b. 결정 6 — 재색인 (권고안, 아직 결정되지 않음)

**이것은 결정이 아니라 권고안이다.** 근거를 적었으니 반대 결정을 하려면 근거를 반박하면 된다.

### 문제 — 그리고 왜 사업 문서에 들어가는가

모델을 바꾸면 기존 벡터가 무효가 된다. 그런데 **무효인지 알 방법이 그래프에 없다** —
어떤 벡터에도 *무슨 모델로 만들었는지* 기록이 없다 (`text2sql_table_vectorizer.py:270-273`).

재색인은 **파괴적 작업**이고, constitution 원칙 IV 가 다루는 영역이다. 그 문서는 추측이 아니라
**실제 사고 두 건**을 근거로 갖고 있다 — 전역 삭제로 data-fabric 카탈로그 소실,
스키마 그룹 삭제 후 엔티티 누적으로 노드 수 두 배 보고.

사업 문서에 넣는 이유: **고객 데이터를 지우는 절차**이기 때문이다. 기술 선택이 아니라
신뢰의 문제다.

### 권고 — 다섯 줄

1. **감지 수단(지문)을 정책보다 먼저 만든다.** 벡터 옆에 모델·차원을 **노드마다** 기록한다.
   전역에만 두면 재색인이 중간에 죽었을 때 "전부 다시" 밖에 못 하고, 수천 테이블에서 그것은
   사실상 복구 불가다.
2. **자동 재색인은 지울 것이 없을 때만.** 벡터가 하나도 없거나 일부만 없으면 자동으로 채운다
   (파괴적이지 않다). **지문 불일치는 확인을 받는다.**
   콜드스타트 판정 로직은 이미 있다 — `text2sql_runtime_repair.py:124-136`.
3. **확인받을 때 무엇을 잃는지 숫자로 보인다** — 대상 테이블·컬럼 수, 예상 시간,
   유료 제공자면 **예상 비용**, 그리고 **되돌릴 수 없다는 사실**.
   *"모델을 바꾸면 다시 색인합니다"* 로는 판단할 수 없다.
4. **삭제 범위를 좁힌다.** 벡터·지문 속성만 지우고 `(:Table)`/`(:Column)` 노드는 건드리지
   않는다 (그것은 data-fabric 카탈로그다). 범위는 **데이터소스 단위**로 좁힌다 —
   그러지 않으면 한 데이터소스의 재색인이 **다른 데이터소스의 벡터를 지운다**.
5. **재색인 중에 거짓말하지 않는다.** 지문이 맞는 노드만 검색 대상으로 삼는다.
   옛 벡터와 새 벡터를 섞어 검색하는 안은 **채택하지 않는다** — 같은 열화를 *숨기기* 때문이다.

### 미결정으로 남기는 것

확인 UI 의 위치(부팅 화면 / 앱 안 설정 / 추출 화면), 대규모에서 지문 필터 검색의 성능,
데이터소스 단위로 나눠 돌릴지 한 번에 돌릴지.

`agent-backend-and-llm-access.md` 가 미해결로 남긴 문제에 대한 답이다.

- **해결되지 않는다**: *모델* 차이. 004 가 이미 Out of Scope 로 선언했다 —

**분석기는 예외다.** 참고 구현(robo-skill-analyzer)은 MCP 를 헌법으로 금지하는데, 근거가 기능이
아니라 프롬프트 캐시다 — *"MCP 툴 정의가 캐시 프리픽스에 얹혀 캐시를 오염시킨다"*

루프가 오케스트레이터일 때만 성립하므로, ontologic 에서는 이렇게 가른다:

| 소비자 | 접근 | 이유 |
|---|---|---|
| 데스크톱 셸 · 게이트웨이 · 프론트 | `POST /robo/analyze` (기존 계약) | 이들은 에이전트가 아니다 |
| cliagents 의미 루프 | **Bash CLI** | 캐시 프리픽스 보존 — 원래 근거가 그대로 성립 |
| deepagents 의미 루프 | **MCP 도구** | 셸이 build 모드에만 있고 120초에 잘린다 |

**같은 결정론 함수를 세 진입점이 공유한다.**

## 6. 결정 8 — text2sql 컨테이너는 남는다. 메모리 이득을 약속하지 않는다

`agent-backend-and-llm-access.md` 는 이렇게 적었다:

> [memory-footprint-measurement.md] 가 잰 text2sql 호스트 프로세스 214.8 MiB 는 이 리팩토링 이후
> **사라질 수 있다.** 8GB 스펙 판단(권장 16GB / 최소 8GB)을 그때 다시 본다.

### 확인한 사실 — 그렇지 않다

| 실측 | 값 | 출처 |
|---|---|---|
| text2sql 호스트 프로세스 (유휴) | 214.8 MiB | §3-2 |
| text2sql 컨테이너 (Podman, 라운드 3) | **201.3 MB** | §10-3 |
| core 소계 | 3,261.8 MB | §10-3 |
| **text2sql 비중** | **6.2%** | 계산 |
| 8GB 판정 근거 | idle 3.957 GiB + OS 2~3 GiB = **5.96~6.96 GiB** (Podman 기준) | §7-2 |

그리고 컨테이너를 없앨 수 없는 이유가 셋 있다:

1. **`POST /text2sql/direct-sql` 이 8곳에서 호출된다** — domain-layer 6곳
   (`app/routers/ontology.py:4655,4879,5575` 등), ontology-studio 1곳, robo-data-catalog 1곳.
   constitution 원칙 I 이 *"실데이터 조회는 이 엔드포인트를 거친다"* 로 못박은 계약이다.
2. **Neo4j 벡터 인덱스 5개와 임베딩 배치 작업을 소유한다.**
3. **`GET /text2sql/meta/*` 가 ontology-studio 의 컬럼 카탈로그 1순위 소스다**
   (`datafabric_client.py:284`).

### 결정

**컨테이너는 남기되 요청 경로를 비운다.** 이득은 메모리가 아니라 **LLM 키 요구의 소멸과 크래시
루프의 제거**다. 메모리는 리팩터링 후 같은 방법으로 재측정해 문서에 라운드를 추가한다 —
**증가/감소 방향을 미리 약속하지 않는다.**

> 사업 문서에서 "text2sql 컨테이너가 사라져 메모리가 준다"고 말하지 않는다. 근거가 없다.
> 메모리의 실제 지렛대는 결정 3(임베딩 모델을 몇 벌 두느냐)이고, 그쪽이 12.3% 대 6.2% 로 크다.

## 7. 결정 9 — 분석기: 참고 구현을 그대로 쓰지 않는다

전 코드가 단일 스쿼시 커밋 1개.

### 결정

**설계를 이식하고 코드는 우리 계약 위에 다시 쓴다.** Neo4j 스키마는 기존
`robo-data-analyzer` 것을 따른다 — robo-data-catalog 와 robo-data-frontend 가 이미 그것을 읽으므로,
스키마를 바꾸면 이 작업 범위가 두 서비스 더 늘어난다.

### 부수 효과 — 하드코딩된 프레임워크 스킬 6개가 사라진다

기존 `robo-data-analyzer/skills/` 에 `ejb-cmp`·`jpa-standard`·`mybatis-ibatis`·`ofbiz`·
`proframe-c-pfm-dbio` + 템플릿, 합계 366줄이 있다. 프레임워크마다 사람이 써 넣은 지식이다.

참고 구현의 scan 2모드는 정확히 이것을 **런타임 발견으로 일반화**한 것이고, 네 프레임워크를
대등한 예시로만 둔 채 *"★범용 — 프레임워크에 하드코딩 금지"* 라고 못박는다.

**사업 관점**: 새 프레임워크를 만날 때마다 코드(스킬 파일)를 추가하지 않아도 된다는 뜻이다.
컨설팅형 사업에서 이것은 단가가 아니라 **리드타임**의 문제다.

**리스크**: 하드코딩에 담긴 도메인 지식(예: ProFrame SQL_KEY 의 두 변종 — 본 테이블 R/W 와
시퀀스 채번 wrapper)이 발견으로 재현되지 않으면 품질이 떨어진다. 대조 단계가 잡아야 한다.

## 9. 단계와 각 단계의 사업적 산출물

명세의 단계 계획을 **무엇을 팔 수 있게 되는가**로 다시 적은 것이다.

| 단계 | 끝나면 말할 수 있는 것 | 위험 |
|---|---|---|
| **T0** 안전망 (골든셋 + 테스트 + 데드코드 900줄 삭제) | (대외적으로 없음) | 낮음 |
| **T1** 임베딩 제공자 심 (openai 제약 제거 + `base_url`) | (대외적으로 없음) — **그러나 이것 없이는 T4 의 선택 화면이 거짓말이 된다** | 낮음 |
| **T2** 지문 (감지 수단) | (대외적으로 없음) | 낮음 |
| **T3** 색인을 메타데이터 증강으로 | **"데이터를 연결하면 색인까지 끝납니다."** 크래시 루프 소멸 | **중간~높음** — 새 단계 신설 |
| **T4** 설정 수집 화면 + 상태 표면화 | **"LLM 키 없이 설치합니다. 데이터 연결할 때 임베딩만 한 번 고르면 됩니다."** ← 사업 가치의 본체 | 낮음 |
| **T5** 재색인 (확인형) | **"모델을 바꿔도 조용히 망가지지 않습니다."** | 중간 (파괴적 작업) |
| **T6** 도구 계층 추출 | (대외적으로 없음) | 중간 |
| **T7** 스킬 + MCP + 두 번째 엔진 | "우리 Text-to-SQL 방법론을 스킬로 가져가실 수 있습니다" (아직 기본 아님) | 중간 |
| **T8** 엔진 전환 | 위 문장이 기본 경로가 됨 | **높음** — 품질 회귀 |
| **T9** 컨트롤러 제거 | 유지보수 비용 감소 | 높음 (되돌리기가 revert) |
| **A1** 결정론 엔진 이식 | (대외적으로 없음) | 낮음 |
| **A2** 새 서비스 골격 | **"키 없이 코드 구조 분석이 끝까지 돕니다."** 증거 11 의 ❌ 가 ✅ 로 | 중간 |
| **A3** 의미 루프 (스킬) | "새 프레임워크에 코드 추가 없이 대응합니다" | 중간 |
| **A4** 병행 대조 → 교체 | 위가 기본 경로 | 높음 |
| **A5** 레거시 제거 | 스택에서 LangGraph 파이프라인 소멸 | 중간 |

**T3~T4 와 A2 가 사업적으로 가장 값진 구간이다.** T4 에서 "첫 실행 경험"이 완성되고,
A2 에서 증거 11 이 멈춘 자리를 지난다. T8·A4 가 진짜 결정 지점이고, 그 앞에
골든셋·대조 리포트라는 판정 근거를 만들어 둔다.

**두 트랙의 유일한 결합점**: 번들 로컬 모델(선택지 3)만 A2 에 걸린다. T3 은
`llm_endpoint`/`openai` 만으로 완주하므로 **A 트랙을 기다리지 않는다.**
그때까지 설정 화면의 세 번째 선택지는 "준비 중"으로 둔다 — **화면에 있는데 안 되는 것보다
낫다.** 초판이 지적한 함정이 바로 그것이다(§4).

- **로컬 OpenAI 호환 서버가 `/v1/embeddings` 를 실제로 서빙하는지** — **미확인.**
  결정 5 의 1순위(우리 스택 메모리 증가 0)가 이 전제 위에 있다. 이 환경에서 왕복을 검증하지
  않았다. **틀리면 400 MB 번들 모델이 1순위로 올라온다.**

  LLM 생성을 **둘 다** 요구한다. 이것을 풀지 못하면 "키 없이"가 색인 단계에서 다시 깨진다.
- **재색인 확인 UI 의 위치와 대규모 성능** — 미결정 (결정 6 은 권고안이다).
- **`indexing` 중 질의를 대기시킬지 부분 결과로 답할지** — 미결정.
- **에이전트 루프의 지연·토큰 비용** — 미측정. 004 의 질문 응답 20.3초가 참고값이지만
  text2sql 은 도구 왕복이 더 많다.
- **메모리 순변화** — 미측정. §6 근거로 큰 변화를 기대하지 않는다.
- **참고 구현의 상위 근거 문서** — 그 헌법이 단일 진실로 지목한
  `docs/HANDOFF-순수skill-analyzer-2026-07-02.md` 가 **그 저장소에 없다.** 레거시 분석기를 왜

- **캐시 프리픽스가 우리 cliagents 경로에서 유지되는지** — 스튜디오는 턴마다

- **`infra/docker-compose.robo-stack.yml` 의 text2sql 환경변수가 현재 코드와 불일치**

  `docker-compose.robo-stack.yml:182-186`). 이 작업 범위인지 별도 수정인지 미결정.
- **새 분석기의 저장소 위치** — 새 서브모듈인지 기존 저장소의 새 패키지인지 미결정.

## 13. 완료 판정

전략 문서 §6 「완료 판정 규칙」을 그대로 적용한다 —
*"구현 작업은 영상 증거 없이 완료로 치지 않는다."*
(`ontology-studio-strategy.md:290-306`)

| 작업 | 증거 디렉터리 | 반드시 담아야 하는 화면 |
|---|---|---|
| T1~T9 | `docs/business/evidence/12-skill-based-text2sql/` | ① 임베딩 미설정에서 앱이 뜨고 데이터소스 질의가 **이유와 함께 거부**되며 온톨로지 설계는 되는 화면 ② 추출 시작 시 **묻는 화면**, 두 번째 실행에서 **묻지 않는 화면** ③ 색인 후 **같은 질문에 답이 나오는** 화면 ④ **재색인 확인 화면**(대상 수·시간·되돌릴 수 없음) |
| A1~A5 | `docs/business/evidence/13-skill-based-analyzer/` | **키 없이 분석이 끝까지 도는 화면.** 신·구 대조 리포트 |

**①→③ 의 순서 자체가 증거다.** 초판은 ③ 하나만 찍으면 되는 줄 알았으나, 개정된 결정에서는
"안 될 때 어떻게 거절하는가"가 제품의 성질이므로 ①·② 없이는 완료로 칠 수 없다.
④ 는 파괴적 작업의 동의 절차이고, **화면으로만 증명된다.**

`README.md` 는 기존 관례를 따른다 — 결론 먼저(단계별 ✅/❌ 표) → 파일 → **안 되는 것 그대로** →
재현 절차 → 함께 고친 것 → 사람이 판단할 것.

**"테스트가 통과했다"는 완료가 아니다.** 이번 리팩터링에서는 특히 그렇다 — 컨트롤러에 테스트가
0개였다는 사실 자체가, 테스트 통과가 이 코드에서 아무것도 보증하지 못했다는 증거다.

## 14. 개정 기록

### 2026-08-03 — 임베딩의 지위와 색인의 자리 (사업 판단)

결정을 덮어 쓰지 않고 **무엇이 뒤집혔는지** 적는다. 전제 문서
`agent-backend-and-llm-access.md` 가 *"결정과 구현 결과를 같은 자리에서 고쳐 쓰면, 나중에
'왜 그렇게 정했나'를 되짚을 근거가 사라진다"* 고 한 것과 같은 이유다.

| | 초판 (같은 날 앞선 판) | 개정 |
|---|---|---|
| 임베딩의 지위 | 선택. 없으면 검색 품질만 떨어짐 | **데이터소스 질의의 필수 선행 조건** |
| 색인이 없을 때 | 벡터축 빼고 **답한다** (저하 모드) | **거부한다.** 답을 지어내지 않는다 |
| 결함의 위치 | text2sql 이 임베딩을 OpenAI 에 고정 | **메타데이터 추출에 색인 단계가 통째로 없다** |
| 색인 소유 | text2sql 기동 잡 | **메타데이터 증강 단계** |
| 로컬 임베딩 비용 | 400 MB 기정사실 | **1순위는 0 MB** (기존 엔드포인트 재사용) |
| 재색인 | "차원 다르면 거부" 한 줄 | **지문·확인·좁은 삭제·필터 검색** (권고안) |
| 대표 카피 | *"키 없이 설치하면 바로 질문"* | *"키 없이 설치하고, 데이터 연결할 때 임베딩만 한 번 고른다"* |
| T 트랙 | 5단계 | **9단계** |

**왜 초판이 틀렸는가.** 초판은 `EMBEDDING_PROVIDER` 가 text2sql 설정이라는 사실에서 출발해
"text2sql 이 임베딩을 잘못 다룬다"로 진단했다. 확인해야 했던 질문은 **누가 벡터를 채우는가**
였고, 답은 "아무도" 였다. **진단이 한 단계 얕았고, 그 위에 세운 `none` 저하 모드 설계가
따라서 틀렸다.**

**초판에서 살아남은 것.** 결정 4 — *임베딩은 스킬로 옮겨지지 않고 도구로 남는다*.
CLI 에이전트가 벡터를 만들 수 없다는 사실은 사업 판단과 무관하게 참이다.

**교훈 하나.** 초판은 "다축 검색이라 폴백이 가능하다"는 **기술적 가능성**을 **제품 결정**으로
바로 옮겼다. 가능한 것과 팔 만한 것은 다르다. 조용히 틀린 SQL 은 Text-to-SQL 제품에서
기능이 아니라 부채다.

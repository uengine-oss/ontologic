# 시연 구성의 순서 — 문서에서 시작해 데이터로 내려간다

이 문서는 **왜 이 순서여야 하는가**를 적는다. 첫 시도에서 순서를 뒤집었다가 되돌린 기록이
함께 있다. 되돌린 이유가 이 플랫폼의 요점이기 때문이다.

---

## 처음에 잘못한 것

첫 구성은 이렇게 했다.

```
PostgreSQL 한 스키마(supplychain, 11개 테이블)
  → 카탈로그에서 클래스를 결정적으로 생성
  → 마스터 5종을 그래프 인스턴스로 적재 (212건)
  → 트랜잭션 6종만 가상 클래스
```

**세 가지가 틀렸다.**

**① 세부 데이터가 지식지도 안으로 들어갔다.** 공급사 18건, 품목 36건, 계약 31건, 발주
119건이 Neo4j 노드로 복제됐다. 지식지도가 **데이터의 사본**이 된 것이다. 그러면 원본이
바뀔 때 지도가 낡고, 지도의 크기가 데이터의 크기를 따라간다. 지식지도는 사본이 아니라
**읽는 방법**이어야 한다.

**② 시스템이 하나였다.** 데이터 패브릭이 하는 일은 한 스키마의 테이블을 읽는 것이 아니라,
**서로 다른 시스템에 흩어진 것을 잇는 것**이다. 한 스키마에 다 넣으면 연계 계층은 아무 일도
하지 않는 셈이고, 시연이 증명하는 것도 없다.

**③ 문서가 없었다.** 테이블 구조에서 클래스를 만들면 나오는 것은 **테이블의 그림자**뿐이다.
`ScmPurchaseOrder` 는 `scm_purchase_order` 의 다른 이름일 뿐, 업무가 다루는 개념이 아니다.
그래서 "납기리스크", "페널티발동요건", "재고커버일수" 같은 **판단**이 지도 어디에도 없었다.
그런 개념이 없으면 "발주 상태가 DELAYED"라는 사실은 있어도 "이 건이 페널티 대상인가"라는
답은 나오지 않는다.

## 바로잡은 순서

```
① 개념 문서                     docs/공급망관리-개념체계.md
      │                          업무가 무엇을 다루고 무엇을 판단하는가
      ▼
② 문서 기반 온톨로지 구축        스튜디오 구축 모드 (문서 + 골든 퀘스천)
      │                          개념 클래스 + 관계 + 업무 규칙
      ▼
③ 데이터 패브릭 연계            4개 이기종 시스템 등록·메타데이터 추출
      │
      ▼
④ 개념 ↔ 데이터 바인딩          기록 개념 → 가상 클래스 (그래프 복제 0)
      │                          판단 개념 → 개념 노드 (데이터 없음)
      ▼
⑤ 에이전트 실행 + 보드 시각화    골든 퀘스천에 답하고 결과를 위젯으로
```

## ① 개념 문서

[`docs/공급망관리-개념체계.md`](docs/공급망관리-개념체계.md). 어느 시스템에 어떤 테이블이
있는지가 아니라 업무의 개념 체계를 적는다. 핵심은 **개념을 두 층으로 나눈 것**이다.

| | 기록되는 개념 (11종) | 판단되는 개념 (9종) |
|---|---|---|
| 예 | 공급사·품목·계약·발주·선적·통관신고·재고·고객·주문·클레임 | 납기리스크·페널티발동요건·재고커버일수·안전재고이탈·대체소싱후보·공급중단영향 |
| 데이터 | 기간계 시스템에 **있다** | 어느 시스템에도 **없다** |
| 지도에서 | 데이터소스에 바인딩된 가상 클래스 | 개념 노드 (바인딩 없음) |
| 그래프 인스턴스 | **0건** | **0건** |

판단 개념은 기록 개념을 **가리키기만** 한다. 스스로 데이터를 갖지 않는다. 이것이 지식지도가
데이터 사본이 아닌 이유다.

문서에는 업무 규칙 9개(R1~R9)와 골든 퀘스천 6개도 함께 적는다. 규칙은 값이 아니므로
시스템이 아니라 온톨로지에 있어야 한다.

## ③ 이기종 시스템 — 표기가 다른 채로 둔다

| 시스템 | DB | 테이블 | 담는 개념 |
|---|---|---|---|
| **ERP** 구매·조달 | PostgreSQL `erp` | 5 | 공급사·품목·계약·발주·발주라인 |
| **관세·통관** | PostgreSQL `customs` | 1 | 통관신고 |
| **WMS** 창고·운송 | MySQL `wms` | 2 | 선적·일별재고 |
| **CRM** 고객관리 | MySQL `crm_scm` | 3 | 고객·주문·클레임 |

**키 표기를 통일하지 않았다.** 실제 기업이 그렇기 때문이다.

| 개념 | ERP | WMS | CRM | 관세 |
|---|---|---|---|---|
| 품목 | `item_id` | `sku_code` | `sku_code` | `ref_item_code` |
| 공급사 | `supplier_id` | `vendor_code` | — | — |
| 선적 | — | `shipment_no` | — | `ref_shipment_no` |

통관 시스템에는 외래키가 아예 없다. 문자열만 들고 있다. **이 단절을 잇는 것이 온톨로지의
일이고**, 표기를 미리 통일해 두면 그 일이 사라져 시연이 아무것도 증명하지 못한다.

## ⑤ 결과는 보드로 그린다

답이 표와 문장으로만 나오면 그것은 텍스트 도구다. 판정과 집계는 **보드 위젯**으로 그린다 —
KPI, 막대, 시계열, 트리맵 등 18종(spec 011). 어떤 위젯을 쓸지는 객체 유형이 정한다(규칙
O1~O10).

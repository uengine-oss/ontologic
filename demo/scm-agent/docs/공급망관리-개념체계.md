# 기업 공급망 관리 업무 개념 체계

본 문서는 전자부품 수출 제조 중견기업의 공급망 관리 업무를 **개념 수준**에서 정의한다.
어느 시스템에 어떤 테이블이 있는지가 아니라, **업무가 무엇을 다루고 무엇을 판단하는가**를
적는다. 시스템 연계는 이 개념 체계가 정해진 뒤에 붙인다.

---

## 1. 개념의 두 층

공급망 업무의 개념은 성격이 다른 두 층으로 나뉜다. 이 구분이 이 문서의 뼈대다.

### 1-1. 기록되는 개념 (업무 시스템에 데이터가 있다)

거래와 실물의 흐름을 기록한 것이다. 기간계 시스템이 이미 들고 있으므로 **따로 옮겨 적지
않고 있는 자리에서 읽는다.**

- **공급사(Supplier)** — 우리에게 자재를 공급하는 법인. 등급(tier), 평가점수, 리드타임,
  납기준수율을 가진다.
- **품목(Item)** — 조달·생산·판매의 대상. 원자재·반제품·완제품으로 나뉜다. 품목분류
  코드(HS), 원산지, 안전재고, 최소발주수량을 가진다.
- **계약(Contract)** — 공급사와 맺은 거래 조건의 문서. 유효기간, 자동갱신 여부, 페널티율,
  리스크 조항을 가진다.
- **발주(PurchaseOrder)** — 공급사에게 보낸 구매 요구. 약속 납기와 금액을 가진다.
- **발주라인(PurchaseOrderLine)** — 발주에 담긴 품목별 수량·단가.
- **선적(Shipment)** — 발주한 물량의 물리적 운송 건. 출항/도착 예정과 실적, 지연 일수와
  사유를 가진다.
- **통관신고(CustomsDeclaration)** — 선적에 대한 수출입 신고. 신고 품목분류 코드, 원산지,
  협정세율 적용 여부, 원산지증명 첨부 여부, 보류 사유를 가진다.
- **재고스냅샷(InventorySnapshot)** — 특정 시점·창고의 품목 보유량. 가용량, 예약량,
  운송중 수량, 일평균 사용량을 가진다.
- **고객(Customer)** — 완제품을 사는 법인. 납기 약정(SLA), 인도조건을 가진다.
- **고객주문(SalesOrder)** — 고객이 낸 주문. 요청 납기와 확정 납기를 가진다.
- **클레임(ClaimTicket)** — 고객이 제기한 문제. 유형, 심각도, 원인, 연결된 발주·선적을
  가진다.

### 1-2. 판단되는 개념 (어느 시스템에도 데이터가 없다)

업무 담당자의 **판단**이다. 시스템은 이것을 저장하지 않는다. 위 기록들을 규칙에 비추어
읽을 때 비로소 생긴다. 온톨로지가 존재하는 이유가 여기 있다 — 이 개념들이 없으면
"발주 상태가 DELAYED"라는 사실은 있어도 "이 건이 페널티 대상인가"라는 답은 없다.

- **납기리스크(DeliveryRisk)** — 약속 납기를 지키지 못할 가능성과 그 크기.
  선적 지연·통관 보류·재고 부족이 원인이 된다.
- **페널티발동요건(PenaltyTrigger)** — 계약의 지연 페널티 조항이 실제로 발동되는 상태.
  *지연 일수가 조항의 기준 일수를 초과*하면 충족된다.
- **통관보류사유(CustomsHoldReason)** — 통관이 막힌 원인의 유형. 서류 미비(원산지증명
  누락), 품목분류 불일치, 세율 다툼으로 나뉜다.
- **품목분류적합성(HsCodeConformity)** — 신고한 품목분류 코드가 품목 마스터의 코드와
  일치하는가. 불일치는 정정신고 대상이다.
- **재고커버일수(StockCoverDays)** — 현재 가용재고로 며칠을 버티는가.
  *가용재고 ÷ 일평균사용량*으로 계산한다. 어느 테이블에도 저장돼 있지 않다.
- **안전재고이탈(SafetyStockBreach)** — 보유량이 안전재고 아래로 내려간 상태.
- **대체소싱후보(AlternateSourcingOption)** — 주 공급사를 대신할 수 있는 공급사와 그 조건.
  평가점수·리드타임·납기준수율로 비교한다.
- **계약갱신우선순위(RenewalPriority)** — 만기가 임박한 계약 중 먼저 협상해야 할 순서.
  미결 발주 노출액과 자동갱신 여부가 정한다.
- **공급중단영향(SupplyDisruptionImpact)** — 한 공급 사건이 어느 고객 주문까지 번지는가.
  발주 → 부품 → 완제품 → 고객주문의 경로로 추적한다.

## 2. 개념 간 관계

```
공급사 ──공급한다──▶ 품목
공급사 ──체결한다──▶ 계약
계약   ──적용된다──▶ 발주
발주   ──담는다────▶ 발주라인 ──지정한다──▶ 품목
발주   ──운송된다──▶ 선적     ──신고된다──▶ 통관신고
품목   ──보유된다──▶ 재고스냅샷
고객   ──발주한다──▶ 고객주문 ──요구한다──▶ 품목(완제품)
고객   ──제기한다──▶ 클레임   ──지목한다──▶ 고객주문

납기리스크       ──근거로삼는다──▶ 선적 · 통관신고 · 재고스냅샷
페널티발동요건   ──대조한다────▶ 선적(지연일수) · 계약(리스크조항)
통관보류사유     ──설명한다────▶ 통관신고
품목분류적합성   ──대조한다────▶ 통관신고(신고코드) · 품목(마스터코드)
재고커버일수     ──산출된다────▶ 재고스냅샷
안전재고이탈     ──판정한다────▶ 재고스냅샷 · 품목(안전재고)
대체소싱후보     ──비교한다────▶ 공급사
계약갱신우선순위 ──집계한다────▶ 계약 · 발주
공급중단영향     ──추적한다────▶ 발주 → 품목 → 고객주문
```

**판단 개념은 기록 개념을 가리키기만 한다.** 스스로 데이터를 갖지 않는다. 이것이 지식지도가
데이터 사본이 아니라 **읽는 방법**인 이유다.

## 3. 업무 규칙

에이전트가 판단할 때 적용하는 규칙이다. 값이 아니라 규칙이므로 시스템이 아니라 온톨로지에
있어야 한다.

| 규칙 | 내용 |
|---|---|
| R1 페널티 | 선적 지연 일수가 계약 리스크 조항의 기준 일수를 초과하면 페널티 대상이다. 예상액은 발주 금액 × 페널티율이며 **파생값으로 표시**한다. |
| R2 연속위반 | 같은 공급사에서 페널티 대상이 연속 2회 발생하면 계약 해지 검토 대상이다. |
| R3 원산지증명 | 협정세율을 신청한 수입 신고는 원산지증명이 첨부돼야 한다. 없으면 협정세율 적용이 보류되고 기본세율이 적용된다. |
| R4 품목분류 | 신고 품목분류 코드는 품목 마스터의 코드와 일치해야 한다. 불일치는 정정신고 대상이다. |
| R5 커버일수 | 재고커버일수 = (보유량 − 예약량) ÷ 일평균사용량. 운송중 수량은 커버일수에 넣지 않고 **별도로 표시**한다. 도착이 확정되지 않았기 때문이다. |
| R6 안전재고 | 보유량이 안전재고 미만이면 이탈로 판정한다. 이탈 품목은 리드타임과 커버일수를 함께 본다. |
| R7 대체소싱 | 대체 공급사 발주 수량은 최소발주수량의 배수로 올림한다. |
| R8 갱신우선순위 | 만기 임박 계약은 미결 발주 노출액이 큰 순으로, 자동갱신이 없는 것을 먼저 본다. |
| R9 근거제시 | 모든 답변은 근거(어느 시스템의 어느 테이블에서 몇 행)를 함께 밝힌다. 계산으로 얻은 값은 파생값임을 표시한다. |

## 4. 시스템 지형 (연계 대상)

개념은 하나지만 데이터는 **네 개 시스템에 흩어져 있고, 부르는 이름도 다르다.**

| 시스템 | 성격 | 담는 개념 | 비고 |
|---|---|---|---|
| **ERP** (PostgreSQL) | 구매·조달 기간계 | 공급사, 품목, 계약, 발주, 발주라인 | 키: `supplier_id`, `item_id` |
| **WMS** (MySQL) | 창고·운송 | 선적, 재고스냅샷 | 키: `vendor_code`, `sku_code` — ERP 와 **표기가 다르다** |
| **관세·통관** (PostgreSQL) | 수출입 신고 | 통관신고 | ERP·WMS 를 모른다. `ref_shipment_no`·`ref_item_code` 문자열만 들고 있다 |
| **CRM** (MySQL) | 고객관리 | 고객, 고객주문, 클레임 | 키: `cust_no`, `sku_code` |

같은 품목을 ERP 는 `item_id`, WMS·CRM 은 `sku_code`, 통관은 `ref_item_code` 로 부른다.
같은 공급사를 ERP 는 `supplier_id`, WMS 는 `vendor_code` 로 부른다.
**이 표기 차이를 흡수해 하나의 개념으로 잇는 것이 온톨로지의 일이다.**

## 5. 골든 퀘스천

이 지식지도가 답해야 하는 질문이다. 각 질문은 **여러 시스템을 가로지르며**, 답에는
기록만이 아니라 판단이 들어간다.

1. **[조달]** 특정 발주의 납기 리스크는 어떤 상태이며, 계약상 페널티 발동 요건을
   충족하는가?
   → ERP(발주·계약) + WMS(선적)

2. **[수출입]** 통관이 보류·반려된 신고 건의 사유는 무엇이며, 신고한 품목분류 코드가
   품목 마스터와 일치하는가?
   → 관세(신고) + ERP(품목 마스터)

3. **[재고]** 안전재고를 이탈한 품목은 무엇이고, 재고커버일수는 며칠이며, 대체 공급사는
   누구인가?
   → WMS(재고) + ERP(품목·공급사)

4. **[계약]** 만기가 임박한 계약 중 갱신 협상을 먼저 해야 할 것은 무엇이며, 그 근거인
   미결 발주 노출액은 얼마인가?
   → ERP(계약·발주)

5. **[구매]** 특정 품목을 긴급 대체 소싱할 때 주 공급사와 대체 공급사의 조건은 어떻게
   다르며, 최소발주수량을 지킨 발주서 초안은 어떤 내용인가?
   → ERP(품목·공급사) + WMS(재고)

6. **[고객지원]** 고객 클레임의 원인을 주문 → 완제품 → 부품 → 발주 → 선적 → 통관까지
   역추적하면 무엇이 나오며, 고객에게 어떻게 회신해야 하는가?
   → CRM(클레임·주문) + ERP(품목·발주) + WMS(선적) + 관세(신고) — **네 시스템 전부**

6번이 이 지식지도의 존재 이유를 가장 잘 보여준다. 네 시스템 중 어느 하나도 이 질문에
혼자 답할 수 없다.

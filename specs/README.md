# Specifications — ontologic 플랫폼

여기에는 **여러 서비스에 걸치는** 기능 스펙이 들어간다. 하나의 서브모듈 안에서 끝나는 변경은
그 저장소의 `openspec/` 에서 다룬다.

## 여기에 둘 것 / 서브모듈에 둘 것

| | 위치 |
|---|---|
| 공유 Neo4j 그래프의 구조·속성명 계약 | 이곳 (또는 [`docs/catalog-schema.md`](../docs/catalog-schema.md)) |
| 서비스 간 호출 경로·포트·타임아웃 | 이곳 |
| 루트 `.env` 키의 의미와 소유자 | 이곳 |
| 한 서비스 내부의 기능 추가 | 해당 서브모듈의 `openspec/` |

판단 기준은 간단하다 — **한 저장소를 되돌려도 계약이 깨지면 여기에 속한다.**

## 사용법

```
/speckit-specify → /speckit-plan → /speckit-tasks → /speckit-implement
```

**ontologic 루트에서 실행한다.** speckit 스크립트는 `git rev-parse --show-toplevel` 로 저장소
루트를 찾는데, CWD 가 서브모듈 안이면 그 **서브모듈**이 루트로 잡힌다. 그러면 `.specify` 를
찾지 못하거나 `<서브모듈>/specs/` 에 스펙을 만들어 버린다. 서브모듈 코드를 고치는 스펙이라도
스펙 자체는 루트에서 만든다.

모든 plan 의 Constitution Check 는
[`.specify/memory/constitution.md`](../.specify/memory/constitution.md) 의 원칙을 만족해야
한다. 그 문서가 리뷰 기준이고, 카탈로그 계약의 실측 근거는
[`docs/catalog-schema.md`](../docs/catalog-schema.md) 에 있다.

계약을 바꾸는 스펙이라면 구현 전에 다음을 돌려 **현재 상태**를 먼저 확인한다. 계약이 이미
어긋나 있는데 그 위에 설계하면 두 번 고치게 된다.

```bash
uv run --with neo4j python scripts/inspect_catalog.py
```

001~003 은 **역공학**이다 — 설계 문서에서 구현으로 내려간 것이 아니라 동작하는 구현에서
거꾸로 뽑았다. 그래서 각 요구사항에 근거(`↳` 코드·테스트·실측)가 붙어 있고, 검증하지 못한
항목은 "미검증"으로 표시돼 있다. 004 부터는 정방향(spec → plan → tasks)으로 쓴다.

002 는 001 의 대안 진입점이다. 산출물이 같으므로 조회·행위·SQL 안전성·기밀 유지 요구사항은
001 에만 있고 002 는 참조한다. 같은 요구사항을 두 곳에 쓰지 않는다.

004 는 앞의 셋과 축이 다르다. 001~003 이 **무엇을 만드는가**라면 004 는 **누가 만드는가**다.
도구·프롬프트는 그대로 두고 실행 주체만 바꾸므로, 001~003 의 요구사항을 다시 정의하지 않는다.

007 은 004·005 의 연장이다. 004 가 실행 주체를, 005 가 지시문의 위치를 교체 가능하게 만들었는데
그 둘은 **ontology-studio 백엔드 안에서만** 참이었다. `neo4j-text2sql` 과 `robo-data-analyzer` 는
에이전트 백엔드와 무관하게 자기 LLM·임베딩을 직접 부른다. 007 은 그 범위를 두 서비스로 넓힌다.
004 의 요구사항(백엔드 선택·MCP 도구 재사용·프롬프트 단일 소스)을 다시 정의하지 않고 참조한다.

008 은 앞의 것들을 **하나의 시나리오로 잇고 검증한다.** 새 기능을 정의하기보다, 001~003 이 만든
온톨로지 구축 경로와 007 이 옮기는 중인 임베딩·색인이 **실제로 맞물리는지** 묻는다. 방법은 예제를
바꾸는 것이다 — 지금 예제는 이름이 이미 답을 말해줘서 증강의 가치가 증명되지 않는다. 이름을 코드로
바꾸면 전략1의 채점식이 **산술적으로** 0점이 되고(타입 신호도 일치 컬럼이 없으면 함께 죽는다),
그때 비로소 증강된 메타데이터 말고는 근거가 남지 않는다. 실측으로 확인했다 — 목표 개념 13개
전부 `no_match`, 자동 바인딩 0건. 003 FR-006 이 규정했으나 구현되지 않은 "샘플 값 형태 일치"
신호가 여기서 필수가 된다.

011 은 006 의 **뒤쪽 절반**이다. 006 이 "질의 결과에 딸려 나오는 세션 한정 차트"를 설계하고
대시보드 저장·공유·BI 연동을 `Out of Scope` 로 밀어 뒀는데, 011 이 그 자리를 맡는다. 006 의
속성 역할 판정·가드·차트 규칙표(R1~R13)를 **다시 정의하지 않고 승계**하고, 그 위에 객체 유형
축(O1~O10)과 공간·계층·텍스트 위젯을 더한다.

011 이 010 에 의존하는 방식이 앞의 것들과 다르다. 010 이 만든 **MCP 표면을 애플리케이션이 직접
소비한다** — LLM 이 아니라 코드가 도구를 부른다. 그래서 대시보드는 Neo4j 드라이버도 DB 커넥션도
갖지 않고, 010 이 이미 보장한 것(카탈로그·레지스트리 라벨 차단, 바인딩 테이블 밖 SQL 금지,
PII 제거, 읽기 전용)을 코드 한 줄 없이 상속한다.

> 참고: `api-gateway/specs/` 와 `antlr-code-parser/specs/` 는 각자 자기 저장소 범위의 speckit
> 스펙을 이미 갖고 있다. 그쪽으로 옮기지 않았다 — 별도 저장소로 배포되고 자기 constitution
> 을 갖고 있어서, 여기로 끌어오면 서브모듈만 클론한 사람이 스펙을 잃는다.

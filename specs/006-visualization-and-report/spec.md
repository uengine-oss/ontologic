# Feature Specification: 질의 결과 시각화와 리포트 생성

**Feature Branch**: `006-visualization-and-report`

**Created**: 2026-08-02

**Status**: Draft

**Input**: 사업 전략 문서 [`docs/business/ontology-studio-strategy.md`](../../docs/business/ontology-studio-strategy.md)
§5 "시각화·리포트 아키텍처 결정" 및 §6 실행 로드맵 항목 3 — *"speckit spec — 006 시각화 & 리포트"*.
전략 §1 대조표가 이 기능을 **"코드가 0인 유일한 킬러 기능"** 으로 지목했다.

## 관계

[001](../001-datasource-backed-virtual-classes/spec.md) 이 **가상 클래스가 질의 시점에 실제 SQL 로
확장된다**는 것을 만들었고, [004](../004-pluggable-agent-backend/spec.md) 와
[005](../005-portable-agent-skills/spec.md) 가 **그 확장을 누가 어떤 지시문으로 부르는가**를 교체
가능하게 만들었다. 이 스펙은 그 결과가 **사람에게 어떻게 보이는가**를 다룬다.

지금 그 답은 "마크다운 텍스트"뿐이다. 답변 에이전트가 GFM 표를 직접 타이핑하지 않으면 표조차 없다.

루트에 두는 이유는 001·004 와 같다 — 되돌리면 계약이 깨진다:

- 조회 결과 페이로드의 형태. 지금은 `neo4j-text2sql` 이 만들고 `ontology-studio` 가 소비하는데,
  이 스펙은 그 페이로드에서 **버려지고 있는 필드**(`truncated`, `returned_row_count`,
  `max_rows_cap`)를 되살려야 한다. 두 저장소가 함께 지켜야 하는 계약이다.
- 컬럼 타입의 출처. 결과에는 타입이 없고, 타입은 data-fabric 이 쓴 카탈로그에 있다
  (constitution 원칙 I·III).
- SSE 이벤트 계약 — 백엔드와 프론트가 함께 지키는 표면이며, 여기에 새 이벤트가 추가된다.

## 배경 — 왜 지금인가

전략 §1 대조표는 사업안의 전제를 세 덩어리로 나눴다. **이미 된 것**(MCP·온톨로지 구축·Text-to-SQL),
**이식하면 되는 것**(데스크톱 패키징), **새로 만들어야 하는 것**(시각화·리포트·엔터프라이즈).

시각화·리포트는 그 중 **코드가 정확히 0인 유일한 항목**이다. 확인:

- 프론트 의존성은 `cytoscape`(그래프 시각화) · `marked` · `vue` 셋뿐이다.
  ↳ `ontology-studio/frontend/package.json:11-15` — `echarts`/`chart.js` 는 `package-lock.json`
  전이 의존성까지 뒤져도 **0건**
- 백엔드에 PDF 생성·마크다운 변환·템플릿 엔진이 없다. `pdfplumber`/`pypdf` 는 **읽기 전용**이다.
  ↳ `ontology-studio/pyproject.toml:10-31`, 사용처 `document_indexing/ocr_service.py:446,472`
- 채팅 화면에 표를 그리는 코드가 없다. 도구 결과는 `<pre>` 에 원시 JSON 문자열로 접혀 있고,
  답변 본문은 마크다운 렌더 하나뿐이다.
  ↳ `frontend/src/features/chat/ChatPanel.vue:111-114`(도구 결과 `<pre>`) ·
  `ChatPanel.vue:141-143`(본문) · `frontend/src/shared/ui/MarkdownContent.vue:22`

전략 §4-3 이 정한 카피 — *"AI가 우리 회사 DB를 정확히 이해하게 만든다 — 질문하면 차트와
리포트까지"* — 는 이 기능을 전제로 한다. 그리고 §1 이 우선순위를 **3 → 2**(시각화 먼저,
데스크톱 패키징 나중)로 잡은 이유도 여기 있다: *"시각화가 없는 상태로 앱을 배포하면 'SQL 결과를
표로 보는 도구'라는 PoC 인상을 굳히게 된다."*

세그먼트 관점의 근거는 전략 §2 에 있다 — 시각화·리포트는 개발자·분석가 다음의 **세 번째 고객
세그먼트(현업 비즈니스 사용자)** 를 여는 조건이다. 현업 사용자는 JSON 을 읽지 않는다.

## 현재 코드 현실 — 조사 결과

**추측 없이 읽어서 확인한 것만 적었다.** 확인하지 못한 것은 그렇게 표시하고 §미결정 항목으로
내렸다.

### CR-1. 조회 결과는 백엔드 안에서만 온전하고, 밖으로 나가면서 두 번 줄어든다

실행 계층의 결과 구조체 (`run_direct_sql`):

```json
{"status":"ok","columns":["..."],"rows":[{...}],"row_count":123,
 "elapsed_ms":842,"truncated":false,"sql":"SELECT ..."}
```

↳ `ontology-studio/backend/src/modules/ontology/datasource_exec.py:619-627`

여기서 두 번 줄어든다.

| 단계 | 무슨 일이 일어나는가 | 확인 경로 |
|---|---|---|
| ① 도구 반환 | 행이 **30건**으로 잘리고 `truncated_for_agent: true` 가 붙는다 | `tools.py:1567-1578`(`_agent_row_preview`) · 상한 `DATASOURCE_AGENT_ROW_PREVIEW` 기본 **30** — `shared/kernel/settings.py:192` · 호출부 `tools.py:1645, 1786, 1851` |
| ② SSE 송출 | 구조화된 행·컬럼이 **아예 프론트로 가지 않는다.** `datasource_update` 는 스칼라만 싣는다 | `agent_session/service.py:920-940` — 주석 그대로: *"Only scalars the UI needs — never rows, never SQL"* |

`datasource_update` 페이로드는
`{tool, class_name, behavior, row_count, elapsed_ms, binding_kind, datasource, table, error}` 다.

프론트가 도구 결과로 받는 것은 `{name, content}` 뿐이고 `content` 는 **파싱하지 않은 JSON
문자열**이다. ↳ `frontend/src/shared/hooks/useOntologyStudio.js:1078-1090`

**이것이 이 스펙의 첫 번째 제약이다.** 차트를 그리려면 데이터가 있어야 하는데,
**에이전트는 30행만 보고 프론트는 0행을 본다.** 전체 행(최대 500)은 오직 백엔드 도구 함수
안에서만 존재하고 반환 직후 버려진다.

### CR-2. `columns` 는 이름 문자열 배열이다 — 타입 정보가 없다

`columns: List[str]` 로 실행 서비스가 명시적으로 그렇게 선언한다.
↳ `neo4j-text2sql/app/routers/direct_sql.py:73`

소비 측도 이름으로만 다룬다 — `_rows_to_dicts()` 가 `str(column)` 으로 키를 만들어 2D 배열을
dict 로 zip 한다. ↳ `datasource_exec.py:518-531`

타입을 얻을 수 있는 곳은 **결과와 별개인 세 군데**뿐이다:

| 출처 | 형태 | 확인 경로 |
|---|---|---|
| 카탈로그 컬럼 조회 | `{name, type, nullable, primary_key, description}` — `type`/`dtype` divergence 를 여기서 한 번 흡수한다 | `ontology/datafabric_client.py:133-160`(`_normalize_column`) · 조회 `datasource_api.py:93-103` |
| 바인딩의 `column_map` | `[{property, column, type, description, reference}]` | `ontology/schema_ontology.py:270-279` · 저장 `agent_session/session_store.py:436` |
| behavior 의 `output_columns` | 자유형 `list[dict]`, 구조를 강제하는 스키마가 없음 | `datasource_api.py:236-243` · 노출 `tools.py:347-355`. **UI 로 만든 behavior 는 이 값이 항상 `[]`** — `DataSourceBindingPanel.vue:545-557` 이 보내지 않는다 |

그리고 SQL 타입 → 온톨로지 타입 매핑은 **이미 결정적으로 구현되어 있다**:

```python
_TYPE_RULES = (
    (("bool",), "boolean"),
    (("int", "serial"), "integer"),
    (("numeric","decimal","float","double","real","money"), "float"),
    (("timestamp","datetime","date","time"), "date"),
)   # 그 외 "string"
```
↳ `ontology/schema_ontology.py:51-66` (`map_sql_type`)

식별자 판정에 쓸 접미사 목록도 있다 — `_FK_SUFFIXES = ("_id","_no","_code","_key")`
↳ `schema_ontology.py:40`

**즉 차트 추천에 필요한 타입 판정 재료는 이미 저장소 안에 있다.** 새로 발명할 것이 아니라
결과 페이로드에 **연결**하면 된다.

### CR-3. 잘림(truncation) 신호가 지금 틀렸다 — 차트 이전에 고쳐야 한다

세 가지 결함을 확인했다.

1. **실행 서비스가 주는 정확한 신호를 버린다.** `direct_sql.py:69-80` 의 응답 모델에는
   `truncated`, `returned_row_count`, `max_rows_cap` 이 있는데, ontology-studio 는 이 키들을
   **읽지 않는다.** ↳ `datasource_exec.py:612-615` 에 해당 파싱 없음
2. **대신 자체 추정한다.** `"truncated": row_count >= settings.datasource_max_rows`
   ↳ `datasource_exec.py:625`. 전역 상한은 500 (`settings.py:191`) 인데 behavior 별 상한
   기본값은 **200** 이다 (`datasource_api.py:242`, `session_store.py:457`). 200 에 걸려 잘린
   결과는 `truncated: false` 로 보고된다 — **미탐(false negative)**.
3. **자연어 폴백 경로에는 `truncated` 키 자체가 없다.** ↳ `run_react_nl()` 반환
   `datasource_exec.py:729-740`

잘린 데이터로 그린 시계열은 추세를 왜곡하고, 잘린 데이터로 그린 막대는 합계를 틀리게 만든다.
001 이 이미 같은 것을 요구했다 — *"결과가 잘렸으면 답변이 그 사실을 밝혀야 한다"*(001 FR-029).
차트는 그 요구를 **더 엄격하게** 필요로 한다.

### CR-4. 결과 형태가 도구마다 다르다

| 도구 | 행 키 | 컬럼 키 | SQL 키 | `truncated` | 확인 경로 |
|---|---|---|---|---|---|
| `behavior_invoke` | `rows` | `columns` | `sql` | 있음 | `tools.py:1646-1664` |
| `datasource_nl_query` | `rows` | `columns` | **`final_sql`** | **없음** | `tools.py:1852-1873` |
| `entity_fetch`(virtual) | **`entities`** | **없음** | `sql` | 없음 | `tools.py:1787-1801`. 키가 컬럼명이 아니라 **온톨로지 property 명**으로 재매핑된다 (`tools.py:1774-1784`) |
| `entity_fetch`(materialized) | `entities` | 없음 | 없음 | 없음 | `tools.py:1698-1707` |

차트 계층이 이 네 형태를 각각 알면 네 벌의 분기가 생긴다. **하나의 정규화 지점**이 필요하다
(constitution 원칙 III 의 같은 논리 — *"정규화는 서비스별로 한 곳에서만"*).

### CR-5. 에이전트 산출물이 프론트에 도달하는 경로는 **이미 있다** — 3중으로

리포트 export 는 새 배관이 거의 필요 없다.

1. 도구 결과 문자열에서 `/workspace/output/[\w\-\.]+` 를 정규식으로 긁어 `generated_files` 에
   모은다. ↳ `agent_session/service.py:1054-1059`
2. 턴이 끝나면 출력 디렉터리를 통째로 스캔해 `done` 이벤트의 `files` 로 보낸다.
   ↳ `service.py:1737`(`list_output_filenames()`) · `service.py:1830-1838`
   → 프론트 `useOntologyStudio.js:1203-1205` → 메시지 하단 다운로드 버튼 `ChatPanel.vue:146-153`
3. `GET /api/files` 폴링 → `FilePanel.vue`. ↳ `modules/files/api.py:25-29`

다운로드는 `GET /api/download/{filename}` → `FileResponse`.
↳ `modules/files/api.py:41-52`. **단 `media_type` 이 `application/octet-stream` 으로
고정**(`api.py:49`)이라 HTML 리포트도 브라우저에서 열리지 않고 무조건 내려받힌다.

출력 디렉터리 실제 위치: local 백엔드에서 `<LOCAL_SANDBOX_ROOT>/output`, 미설정 시
`<repo>/.cache/sandbox/output/`. ↳ `shared/kernel/settings.py:117-123` ·
`modules/files/workspace.py:53-54`. docker-compose 는 `SANDBOX_BACKEND: local`,
`LOCAL_SANDBOX_ROOT: /workspace` 로 컨테이너 자체를 격리 경계로 쓴다.
↳ `ontology-studio/docker-compose.yml:38-40,57-59`

**결론: 리포트 파일을 출력 디렉터리에 쓰기만 하면 목록·다운로드가 UI 변경 0줄로 성립한다.**

### CR-6. 구조화된 사이드채널 선례가 이미 있다 — `ontology_build_report`

빌드 모드는 에이전트 최종 텍스트에서 펜스 블록을 뽑아 구조화 payload 로 바꾸고, 그것을 전용
Vue 컴포넌트가 렌더한다.

```
_BUILD_REPORT_PATTERN = re.compile(r"```ontology_build_report\s*(\{.*?\})\s*```", re.DOTALL)
```
↳ `service.py:196-199` · 추출 `service.py:544, 1761` · `done` 에 실림 `service.py:1836`
→ 프론트 `useOntologyStudio.js:1200-1202` → `GoldenQuestionReviewPanel` `ChatPanel.vue:179-187`

**이 패턴을 차트에 그대로 쓰면 안 된다.** 저 블록의 내용은 LLM 이 쓴 것이고, 차트 타입은
결정적이어야 하기 때문이다(전략 §5). 선례로서 의미가 있는 것은 *"메시지에 붙는 타입 있는
사이드채널 payload → 전용 컴포넌트"* 라는 **모양**이지 **출처**가 아니다.

### CR-7. 두 에이전트 백엔드는 같은 함수 객체를 공유한다

MCP 브리지는 도구를 재구현하지 않고 `service.py` 의 리스트를 그대로 등록한다.

```python
for tool in tools_for(mode):
    mcp.add_tool(tool)
```
↳ `agent_bridge_mcp/server.py:44-45` · 목록 원천 `server.py:30-35` →
`agent_session/service.py:130-169`(`_BUILD_MODE_TOOLS`) · `service.py:171-182`(`_ANSWER_MODE_TOOLS`)

`server.py:6-7` 주석: *"a tool added there shows up on this surface automatically."*

**따라서 차트 로직을 `modules/ontology/` 의 도구 계층에 두면 deepagents 와 cliagents 양쪽에
자동으로 반영된다.** constitution 의 *"도구를 다시 구현하지 않는다"* 를 지키는 유일한 위치다.

### CR-8. answer 모드에는 쓰기 도구가 없다 — 의도된 경계다

```python
_ANSWER_MODE_TOOLS = [schema_get, entity_search, neo4j_cypher_readonly, graph_stats,
                      vector_search, sandbox_read, behavior_list, behavior_invoke,
                      entity_fetch, datasource_nl_query]
```
↳ `service.py:171-182`

`execute`(임의 셸 실행)와 `sandbox_write` 는 **build 전용**이다 (`service.py:142-145`).
`server.py:14-15` 주석이 이유를 밝힌다 — *"Serving one combined tool set would hand answer mode
write access it does not have today."*

그리고 `sandbox_tools.py` 자체에는 경로 검증이 없다. `/workspace` 로 시작하지 않는 절대경로는
그대로 통과하고(`shared/sandbox/local_backend.py:91-100`), `execute()` 는 `bash -lc` 로
호스트에서 돈다(`local_backend.py:174-180`). 파일 상단이 명시한다 — *"DEV-ONLY: there is no
isolation between the agent and the backend host user."*(`sandbox_tools.py:10`)

**따라서 "에이전트가 matplotlib 스크립트를 짜서 실행해 차트를 만든다"는 답변 모드에서
성립하지 않는다.** 성립시키려면 answer 모드에 `execute` 를 올려야 하고, 그것은 constitution 의
*"모드별 권한을 넓히지 않는다"* 를 정면으로 위반한다.

### CR-9. 답변 스킬은 "파일을 만들지 않는다"고 못박고 있다

> 이 스킬은 파일을 만들지 않습니다. 조회 결과만 다룹니다.

↳ `ontology-studio/skills/ontology-answer/SKILL.md:55`

결과 제시 규칙(`SKILL.md:74-91`)도 텍스트 답변만 규정한다 — 근거 노드, 데이터소스·테이블·행 수,
`truncated_for_agent` 고지. **차트·표·파일 산출에 대한 언급이 전혀 없다.**

리포트 생성을 답변 모드에 넣는다면 이 문장을 고쳐야 한다. 그리고 constitution 이 요구하는 대로
**지시문은 `SKILL.md` 에서만 고친다** — 파이썬에서 조립하지 않는다.

### CR-10. PDF·차트 렌더 수단 현황

| 수단 | 상태 | 확인 경로 |

| 마크다운 → HTML (백엔드) | **없음** — `markdown`/`markdown-it-py`/`mistune` 전부 0건 | `uv.lock` |
| 템플릿 엔진(`jinja2`) | **없음** | `uv.lock` |

## 아키텍처 결정

### AD-1. 차트 스펙은 **도구 계층에서 결정적으로 계산**한다

전략 §5 가 정한 *"차트 추천은 결정적 로직. LLM 에 차트 타입을 묻지 않는다"* 를 코드 위치로
번역하면 답이 하나로 좁혀진다.

- **에이전트가 계산할 수 없다.** 30행만 본다 (CR-1). 카디널리티·행 수·값 범위를 잘못 판단한다.
  그리고 LLM 출력은 비결정적이다.
- **프론트가 계산할 수 없다.** 0행을 본다 (CR-1).
- **`service.py`(SSE 계층)에서 계산하면 절반만 맞는다.** 여기 도달하는 `content` 는 이미 30행으로
  잘린 도구 반환값이다 (`service.py:1065-1066` 는 `_agent_row_preview` **이후**에 호출된다).
- **`modules/ontology/tools.py` 안, 잘라내기 직전이 유일하게 전체 행이 있는 지점이다**
  (`tools.py:1645` 의 `_agent_row_preview()` 호출 직전). 그리고 이 위치는 CR-7 덕분에 두 에이전트
  백엔드에 자동 반영된다.

**결정**: 차트 스펙 계산은 `modules/ontology/` 의 새 모듈(예: `chart_spec.py`)에 두고,
`behavior_invoke` · `datasource_nl_query` · `entity_fetch` 가 **행을 자르기 전에** 호출한다.

### AD-2. 차트 표시는 **직접 경로**(자동), 리포트 조립은 **에이전트 경로**(도구)

이것이 이 스펙에서 가장 중요한 갈림길이다. 양쪽 장단점을 먼저 적는다.

**(A) 에이전트가 도구로 차트를 만든다**

| | |
|---|---|
| 장점 | 사용자가 원할 때만 그린다. 여러 결과를 조합한 차트가 가능하다. 외부 CLI 사용자(005 단독 실행)도 같은 도구를 쓴다 |
| 단점 | **에이전트가 호출을 잊으면 차트가 없다** — 매 질의마다 신뢰할 수 없다. 턴이 하나 늘고 토큰·지연이 는다. 인자를 LLM 이 채우므로 "결정적"이라는 전제가 입력 단에서 무너진다. answer 모드는 파일 쓰기 권한이 없어(CR-8) 실제로 그릴 수단이 없다 |

**(B) 결과가 오면 자동으로 그린다 (직접 경로)**

| | |
|---|---|
| 장점 | 결정적이다 — 같은 결과는 항상 같은 차트. 추가 턴·토큰·지연이 0. 에이전트 권한을 넓히지 않는다. `datasource_update` 를 이미 쏘는 지점(`service.py:1065-1066`)에 얹으면 배선이 짧다. 에이전트가 무엇을 하든 결과가 나오면 반드시 보인다 |
| 단점 | 원하지 않는 차트가 뜰 수 있다. 여러 결과를 합친 차트를 만들 수 없다. **스튜디오 프론트엔드가 없는 단독 스킬 사용자(005)에게는 아무것도 보이지 않는다** |

**결정**: **차트는 (B), 리포트는 (A).** 산출물의 성격이 다르기 때문이다.

- 차트는 **결과의 성질**이다. "이 결과는 시계열이다"는 사용자의 의도와 무관하게 참이다.
  따라서 물어볼 것이 없고, 자동이 옳다. (B) 의 단점 "원하지 않는 차트"는 §차트 추천 규칙의
  **폴백 규칙**(어떤 규칙에도 안 걸리면 차트를 그리지 않는다)과 UI 접기로 흡수한다.
- 리포트는 **사용자의 의도**다. "무엇을 리포트에 담을지"는 결과에서 도출되지 않는다. 어떤 질의
  결과들을 묶을지, 어떤 순서로 배치할지, 어떤 문장을 붙일지는 대화 맥락에만 있다. 이것은
  에이전트가 아니면 알 수 없다.

리포트를 에이전트 도구로 두면 CR-8·CR-9 를 반드시 지켜야 한다:

- 도구는 **`_ANSWER_MODE_TOOLS` 한 곳에만** 추가한다. 그래야 내장 경로와 MCP 표면이 정확히 같다
  (constitution — *"내장 에이전트가 가진 권한과 정확히 같아야 한다"*).
- 도구는 **임의 코드 실행이 아니다.** 인자는 `result_id` 목록과 제목·인사이트 문장뿐이고,
  파일명과 경로는 도구가 정한다. `execute` 를 answer 모드에 올리지 않는다.
- 이것은 answer 모드가 "아무것도 쓰지 않는다"에서 "출력 디렉터리에 리포트 파일만 쓴다"로
  **좁게 넓어지는 것**이다. 숨기지 않고 이 스펙에 적고, constitution 개정 여부를 §미결정으로
  올린다.
- `SKILL.md:55` 의 *"파일을 만들지 않습니다"* 는 **스킬 파일에서** 고친다. 파이썬에서 지시문을
  조립하지 않는다 (constitution — *"지시문과 값을 섞지 않는다"*).

### AD-3. 전체 결과는 **결과 저장소**에 보관하고, 밖으로는 참조(`result_id`)만 낸다

차트도 리포트도 전체 행이 필요한데, 지금은 도구가 반환하는 순간 사라진다 (CR-1).

**결정**: 세션 단위 결과 저장소를 둔다. 도구가 결과를 만들 때 `result_id` 를 발급하고 전체 행과
컬럼 프로파일을 함께 보관한다. 도구 반환값에는 `result_id` 만 실린다.

이것이 없으면 리포트를 만들 때 **SQL 을 다시 돌려야 한다.** 그건 두 가지로 나쁘다 —
MindsDB view 질의가 10~25초 걸리고(constitution 원칙 VI), 두 번째 실행이 첫 번째와 다른 행을
돌려주면 리포트의 차트와 본문이 어긋난다.

기밀 유지는 001 FR-021·022 와 constitution 원칙 V 를 그대로 따른다 — **저장소에는 SQL 을 보관해도
되지만 밖으로 나가는 어떤 payload 에도 SQL·접속정보를 싣지 않는다.**

### AD-4. 리포트의 정본은 **Markdown**이다. HTML·PDF 는 브라우저가 있는 쪽이 만든다

CR-10 이 확인한 대로 백엔드에는 md→html 도, PDF 엔진도, 차트 렌더러도 없다. 그리고 전략 §4-1 의
실측(idle 5.36 GiB, 권장 16GB)은 **백엔드 이미지에 Chromium 이나 WeasyPrint 를 더 넣는 선택을
사실상 봉쇄한다.**

선택지와 비용:

| 선택지 | 비용 | 판정 |
|---|---|---|
| 백엔드에 WeasyPrint | 파이썬 패키지 + cairo/pango 시스템 라이브러리 + CJK 폰트(미확인) | **기각** — 이미지 비대, 전략 §4-1 과 충돌 |
| 백엔드에 Playwright + Chromium | 브라우저 다운로드로 이미지가 수백 MB 늘어난다 | **기각** — 같은 이유. 게다가 로컬 Chromium 이 이미 두 벌(Electron) 생긴다 |
| 백엔드에 ReportLab | 시스템 의존성 없음. 다만 HTML 을 받지 못해 리포트를 다시 조판해야 하고 CJK 폰트 등록이 필요 | **기각** — 마크다운 정본과 별개의 레이아웃 코드가 생긴다 |
| LibreOffice `soffice --convert-to pdf` | 바이너리는 "일부" 있으나 Writer 가용 여부 **미확인**, 호출 코드 0건, 원래 소비자 파일도 사라짐 | **기각** — 없는 것으로 취급한다 |
| **프론트엔드 인쇄(브라우저 print + 인쇄 전용 스타일시트)** | **의존성 0.** 오늘 동작한다 | **채택 (v1)** |
| **Electron `webContents.printToPDF()`** | 의존성 0 (Chromium 이 이미 셸이다). 전략 §5 가 이미 같은 판단을 적었다 | **채택 (작업 7 이후)** |

**결정**:

- **MD** — 백엔드가 항상 생성한다. 출력 디렉터리에 쓰면 CR-5 로 다운로드가 자동 성립한다.
  차트는 `chart_spec` 을 담은 펜스 블록으로 마크다운 안에 보존한다 (텍스트로도 자립한다).
- **HTML** — 프론트가 `marked` 로 렌더하고, 차트는 ECharts 가 **SVG 문자열로 구워** 인라인한다.
  결과 HTML 은 자바스크립트가 0인 정적 문서가 된다. ECharts 번들(수백 KB~1MB)을 리포트마다
  인라인하지 않아도 되고, PDF 변환이 자명해진다.
- **PDF** — 그 HTML 을 브라우저가 인쇄한다. 새 의존성이 없다.

**따라서 export 능력은 실행 환경에 따라 다르다. 이 사실을 숨기지 않고 스펙에 적는다** (§리포트
구조 표 참조).

### AD-5. 차트는 **재집계하지 않는다**

001 FR-028 이 이미 못박았다 — *"숫자는 조회 결과를 인용하고 직접 계산하지 않는다. 집계는 SQL 이
한다."* 차트 계층도 같은 규칙을 따른다. 규칙이 집계를 필요로 하면 그 규칙은 **적용되지 않고**
표로 폴백한다. 차트는 순수한 표현 계층이다.

이유는 정확성만이 아니다. 차트가 재집계하면 화면의 숫자와 답변 텍스트의 숫자가 달라질 수 있고,
사용자는 어느 쪽이 맞는지 알 방법이 없다.

## 차트 추천 규칙

### 1단계 — 컬럼 역할 판정 (결정적)

각 컬럼에 정확히 하나의 역할을 부여한다. 우선순위 순으로 판정하고, 처음 맞는 것을 쓴다.

| 순위 | 판정 | 역할 | 근거 |
|---|---|---|---|
| 1 | `key_columns` 에 포함 · `column_map[].reference == true` · 이름이 `_FK_SUFFIXES` 로 끝남 | `identifier` | 식별자는 숫자여도 측정값이 아니다. 주문번호를 합산하면 안 된다. ↳ `schema_ontology.py:40,276` |
| 2 | 선언 타입 `date` | `temporal` | 바인딩·카탈로그의 타입이 값 추론보다 정확하다 |
| 3 | 선언 타입 `integer`/`float` | `numeric` | |
| 4 | 선언 타입 `boolean`/`string` | `categorical` | |
| 5 | 선언 타입이 없을 때(자연어 폴백의 파생 컬럼 등) 값 기반 추론 | 아래 | `COUNT(*)`·`AVG(x)` 같은 컬럼은 어느 테이블에도 없다 (CR-2) |

타입 출처 우선순위: **바인딩 `column_map[].type` → 카탈로그 `_normalize_column().type` →
값 기반 추론.** 앞의 둘은 `map_sql_type()` 을 그대로 통과시킨다 — 새 매핑표를 만들지 않는다
(`schema_ontology.py:59-66`).

값 기반 추론 규칙(마지막 수단):

- 비-null 값이 전부 ISO 8601 날짜/시각 문자열이거나 date/datetime 객체 → `temporal`
- 비-null 값이 전부 int/float(bool 제외) → `numeric`
- 그 외 → `categorical`
- 비-null 값이 0건 → `unknown` (그 컬럼은 차트에 쓰지 않는다)

### 2단계 — 가드 (규칙 판정 이전에 적용)

| 가드 | 조건 | 동작 | 근거 |
|---|---|---|---|
| **G1** | `status != "ok"` | 차트 없음 | 실패한 조회는 그릴 것이 없다. 001 이 요구한 "조회 실패를 데이터 없음으로 말하지 않는다"와 같은 정신 |
| **G2** | `row_count == 0` | 차트 없음 | 빈 축은 "데이터가 0" 으로 오독된다 |
| **G3** | 잘림이 확인됨 **그리고** 후보 차트가 시계열(R3·R4) | 차트 없음, 표 + 잘림 배지 | 잘린 시계열은 추세를 왜곡한다. 없는 것보다 나쁘다 |
| **G4** | 잘림이 확인됨 (그 외 차트) | 차트를 그리되 **"상위 N건만"** 배지를 반드시 병기 | 001 FR-029 |
| **G5** | 컬럼 수 > 30 또는 행 수 > 5,000 | 차트 없음 | 상한 500(`settings.py:191`)에서 5,000 은 도달하지 않지만, 설정을 올린 환경에서 브라우저를 지키는 방어선 |
| **G6** | `numeric` 컬럼 0개 | 차트 없음 | 측정할 것이 없다 |

G3·G4 는 CR-3 의 잘림 신호 수정에 의존한다. **그 수정이 이 기능의 선행 작업이다.**

### 3단계 — 차트 규칙표 (위에서부터 첫 번째로 맞는 규칙 하나만 적용)

표기: `T`=temporal, `N`=numeric, `C`=categorical, `k(C)`=그 범주 컬럼의 서로 다른 값 개수.
`identifier`·`unknown` 컬럼은 규칙 판정에서 **제외**하고 표에는 남긴다.

| # | 조건 | 차트 | 근거 |
|---|---|---|---|
| **R1** | 행 1 · N=1 · C=0 · T=0 | **KPI (큰 숫자)** | 점 하나에는 축이 필요 없다. 막대 하나는 비교 대상이 없어 정보량이 오히려 준다 |
| **R2** | 행 1 · N 2~6 · C=0 · T=0 | **KPI 묶음** | 같은 이유. 단위가 서로 다를 수 있으므로 한 축에 올리지 않는다 |
| **R3** | T=1 · N≥1 · C=0 · 행 ≥ 3 | **line** (N개 시리즈) | 시간은 순서가 있는 연속 축이다. 막대는 순서를 강조하지 못하고 행이 늘수록 읽히지 않는다 |
| **R4** | T=1 · N=1 · C=1 · k(C) ≤ 8 · 행 ≥ 3 | **다중 시리즈 line** | 범주별 추세 비교. 8 초과는 선이 엉켜 판독이 불가능해진다 |
| **R5** | T=1 · N=1 · C=1 · k(C) > 8 | **표만** | 시리즈가 너무 많다. 상위 N 만 그리면 사용자가 모르는 채 데이터가 잘린다 — G4 와 같은 정신 |
| **R6** | T=0 · C=1 · N=1 · 2 ≤ k(C) ≤ 25 · 값에 음수 포함 **또는** 비율성 아님 | **bar** (k(C) > 12 이면 가로 bar) | 범주는 비연속이므로 선으로 잇지 않는다. 라벨이 많거나 길면 가로가 읽힌다 |
| **R7** | T=0 · C=1 · N=1 · 2 ≤ k(C) ≤ 7 · 모든 값 ≥ 0 · **비율성** | **pie** | 파이는 부분-전체 관계에만 정당하다. 조각 7개를 넘으면 각도 비교가 불가능하다. 기본은 bar 이고 비율성일 때만 pie 로 간다 |
| **R8** | T=0 · C=1 · N=1 · k(C) > 25 | **표만** | 막대 25개를 넘으면 라벨이 겹쳐 못 읽는다 |
| **R9** | T=0 · C=2 · N=1 · k(C₁) ≤ 15 · k(C₂) ≤ 15 | **heatmap** | 두 범주축의 교차값은 격자가 자연스럽다. 15×15 = 225 셀이 판독 한계 |
| **R10** | T=0 · C=0 · N=2 · 행 ≥ 10 | **scatter** | 두 연속 변수의 관계. 10점 미만이면 분포라고 부를 수 없다 |
| **R11** | T=0 · C=1 · N=2 · k(C) ≤ 8 · 행 ≥ 10 | **scatter (범주별 색)** | R10 + 그룹 구분 |
| **R12** | 지리 컬럼쌍(위도/경도 등)이 감지됨 | **표만 — v1 범위 밖** | 지도 타일은 외부 네트워크가 필요하다. *"클라우드 전송 없음"*(전략 §4-1 카피 전략)과 정면으로 충돌한다 |
| **R13** | **그 외 전부** | **표** | **폴백. 억지로 그리지 않는다** |

**"비율성"의 판정도 결정적이어야 한다.** 다음 중 하나면 비율성으로 본다:

1. 수치 컬럼 이름이 `ratio` / `rate` / `pct` / `percent` / `비율` / `비중` / `점유` 중 하나를 포함
2. 모든 값이 0 이상이고 합이 100 ± 0.5 이거나 1.0 ± 0.005
3. 수치 컬럼 이름이 `cnt` / `count` / `건수` / `수량` 을 포함하고 모든 값이 0 이상

세 조건 모두 아니면 bar 다. **애매하면 bar** — 파이를 잘못 쓰는 비용이 막대를 잘못 쓰는 비용보다
크다.

### 4단계 — 산출

규칙이 하나 정해지면 **어떤 규칙이 왜 발동했는지**를 함께 낸다(`rule: "R3"`, `reason`).
디버깅용이 아니라 **사용자용**이다 — 자동으로 뜬 차트는 왜 그 모양인지 말할 수 있어야 신뢰된다.
그리고 사용자가 차트 타입을 수동으로 바꿀 수 있게 한다(세션 한정, 저장하지 않음 — 저장·공유는
Enterprise).

## 리포트 구조와 export

### 리포트 구조

```
제목                       ← 사용자 요청 또는 첫 질문에서 도출
생성 시각 · 출처 요약        ← 데이터소스·테이블·행 수 (001 FR-028)
────────────────────────
섹션 N개, 각 섹션은:
  질문 (사용자 원문)          ← 005 FR-057 과 같은 원칙: 원문을 변형하지 않는다
  차트 (있으면)              ← 결정적 규칙의 산출. LLM 이 고르지 않았다
  표 (상위 M행)              ← 전체 행은 저장소에 남고, 리포트에는 상한을 둔다
  인사이트 문장              ← 여기만 LLM 이 쓴다
  근거 (datasource.schema.table · 행 수 · 잘림 여부)
────────────────────────
꼬리말: 각 섹션의 조회 시각, 잘림 고지, 이 리포트가 어떤 온톨로지/스키마를 근거로 하는지
```

**LLM 은 인사이트 문장에만 쓴다** (전략 §5). 차트 타입·표·근거·수치는 전부 결정적으로 채워진다.
인사이트 문장이 없어도 리포트는 성립해야 한다 — LLM 이 실패하면 그 섹션만 문장이 비고, 리포트
자체는 나온다.

### export 포맷별 처리

| 포맷 | 생성 주체 | 차트 처리 | 의존성 | 어디서 되는가 |
|---|---|---|---|---|
| **MD** | 백엔드 (도구) | `chart_spec` 을 펜스 블록으로 보존 + 표 | **없음** | 항상. 단독 스킬 사용자(005)도 포함 |
| **HTML** | 프론트엔드 | ECharts → **SVG 문자열 인라인**. 결과 문서에 JS 0 | `marked`(있음) + ECharts(신규) | 스튜디오 프론트엔드가 열려 있을 때 |
| **PDF** | 브라우저 | HTML 그대로 인쇄 | **없음** (인쇄 전용 스타일시트만) | 스튜디오 프론트엔드. Electron 이후에는 `printToPDF()` |

MD 는 **정본**이다. HTML·PDF 는 MD + `chart_spec` 에서 파생되며, 파생 경로가 없는 환경(헤드리스,
단독 CLI)에서는 MD 만 나온다. **이 제약을 사용자에게 숨기지 않는다.**

MD 파일은 출력 디렉터리에 쓴다. 그러면 CR-5 의 3중 경로로 목록·다운로드가 **UI 변경 없이**
성립한다. 단 CR-5 가 지적한 `media_type` 고정(`files/api.py:49`) 때문에 HTML 을 브라우저에서
바로 열려면 그 한 줄은 고쳐야 한다.

## 데이터 계약

### QueryResult (백엔드 내부 · 전체 충실도 · 밖으로 나가지 않는다)

```
result_id      : 세션 안에서 유일
tool           : "behavior_invoke" | "datasource_nl_query" | "entity_fetch"
class_name     : 대상 클래스 (있으면)
behavior       : behavior 이름 (있으면)
source         : {datasource, schema, table}
columns        : [컬럼명]           ← CR-2 대로 이름만 온다
rows           : [dict]             ← 전체 (최대 DATASOURCE_MAX_ROWS)
row_count      : 실제 행 수
truncated      : 실행 서비스가 보고한 값 (CR-3 수정 후)
truncated_by   : "engine" | "behavior_max_rows" | "global_max_rows"
elapsed_ms     : 소요 시간
sql            : 실행된 SQL — **저장은 하되 어떤 외부 payload 에도 싣지 않는다**
created_at     :
```

CR-4 의 네 가지 형태를 **여기 하나로 정규화**한다. `entity_fetch` 의 `entities` 는 `rows` 로,
없는 `columns` 는 첫 행의 키에서 도출한다. constitution 원칙 III 과 같은 논리 — 정규화는 한 곳.

### ColumnProfile (파생 · 결정적)

```
name           :
role           : "temporal" | "numeric" | "categorical" | "identifier" | "unknown"
declared_type  : "string"|"integer"|"float"|"boolean"|"date" | null
type_source    : "binding" | "catalog" | "inferred"
distinct_count : 범주 카디널리티 (categorical 일 때)
null_count     :
min / max      : numeric·temporal 일 때
```

`type_source` 를 남기는 이유: 추론으로 정한 타입 때문에 이상한 차트가 나왔을 때, 카탈로그를
고쳐야 하는지 추론 규칙을 고쳐야 하는지 구분할 수 있어야 한다.

### ChartSpec (프론트로 건너가는 것)

```
result_id      :
rule           : "R3" 등 — 어떤 규칙이 발동했는가
chart_type     : "line"|"bar"|"bar_horizontal"|"pie"|"scatter"|"heatmap"|"kpi"|"none"
reason         : 사람이 읽을 한 문장 ("시간 축 1개와 수치 2개 → 시계열 선그래프")
encoding       : {x:{column,role}, y:[{column}], series:{column}|null}
series         : 렌더에 필요한 최소 데이터 (원본 rows 전체가 아님)
notes          : ["상위 500건만 표시" 등]
fallback       : true 이면 표만 그린다
```

**금지**: `sql`, `final_sql`, 접속 정보, 내부 경로는 ChartSpec 에 **절대** 넣지 않는다
(constitution 원칙 V · 001 FR-021·022).

### SSE 이벤트

기존 이벤트 계약(`status`·`token`·`tool_start`·`tool_result`·`todos`·`ref_file`·`neo4j_update`·
`datasource_update`·`schema_created`·`traversed_nodes`·`skill_loaded`·`steered`·`ask_user`·
`error_event`·`node_update`·`done`)에 **하나를 더한다**:

```
event: chart_ready
data: {"result_id": "...", "chart_spec": {...}}
```

`datasource_update` 는 **손대지 않는다.** 그 이벤트의 계약은 *"never rows, never SQL"* 이고
(`service.py:923`) 그것은 진행 상황 칩의 계약으로 여전히 옳다. 데이터를 실어야 하는 것은 다른
이벤트다.

`done` 이벤트는 그대로 두고, 리포트 파일은 기존 `files` 필드로 나간다 (CR-5).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 물으면 차트가 함께 나온다 (Priority: P1)

현업 사용자가 "지난 30일 설비별 불량률 추이" 를 묻는다. 답변 텍스트와 함께 **선 그래프**가 채팅
안에 그려진다. 사용자가 차트를 요청하지 않았고, 차트 종류를 고르지도 않았다.

**Why this priority**: 이 스펙의 존재 이유다. 전략 §4-3 의 카피가 이것 하나에 걸려 있다.

**Independent Test**: 시계열 결과를 내는 behavior 를 호출하는 질문 하나를 던지면, 추가 조작
없이 선 그래프가 렌더된다.

**Acceptance Scenarios**:

1. **Given** 시간 컬럼 1개와 수치 컬럼 1개를 돌려주는 조회, **When** 답변이 끝난다,
   **Then** 선 그래프가 채팅 안에 렌더되고, 어떤 규칙으로 그 차트가 정해졌는지 한 문장으로
   표시된다.
2. **Given** 같은 질문을 두 번 던진다, **When** 두 답변을 비교한다, **Then** **차트 타입이
   동일하다.** LLM 의 문장은 달라질 수 있어도 차트는 달라지지 않는다.
3. **Given** 어떤 규칙에도 걸리지 않는 결과(자유 텍스트 컬럼 여러 개), **When** 답변이 끝난다,
   **Then** 차트를 그리지 않고 표만 보여준다. **억지로 그리지 않는다.**
4. **Given** 조회가 실패했다, **When** 답변이 끝난다, **Then** 차트 영역이 나타나지 않고
   실패 사유가 보인다. 빈 차트를 그리지 않는다.
5. **Given** 결과가 상한에 걸려 잘렸다, **When** 차트가 그려진다, **Then** "상위 N건만" 배지가
   차트에 **반드시** 함께 표시된다.
6. **Given** 결과가 잘렸고 후보 차트가 시계열이다, **When** 답변이 끝난다, **Then** 차트를
   그리지 않고 표 + 잘림 고지만 보여준다.

### User Story 2 - 결과를 리포트로 내보낸다 (Priority: P1)

사용자가 몇 가지를 물어본 뒤 "지금까지 내용을 리포트로 만들어줘" 라고 말한다. 질문·차트·표·
근거·요약 문장이 담긴 리포트 파일이 만들어지고, 채팅에서 바로 내려받을 수 있다.

**Why this priority**: 전략 §2 가 말한 세 번째 세그먼트(현업 비즈니스 사용자)는 화면을 보는 것이
아니라 **문서를 돌린다.** 차트만 있고 내보낼 수 없으면 도구는 여전히 개발자용이다.

**Independent Test**: 두 개의 데이터 질의를 한 뒤 리포트 생성을 요청하면, 두 섹션을 가진 MD
파일이 출력 목록에 나타나고 다운로드된다.

**Acceptance Scenarios**:

1. **Given** 이번 세션에서 조회 결과가 2건 있다, **When** 리포트 생성을 요청한다, **Then**
   두 질문·두 차트·두 표·각각의 근거를 담은 MD 파일이 만들어지고 채팅에 다운로드 버튼이 뜬다.
2. **Given** 리포트가 만들어졌다, **When** 파일 목록을 연다, **Then** 같은 파일이 출력 파일
   목록에도 보인다 (새 배관 없이 기존 경로로).
3. **Given** 리포트의 각 섹션, **When** 내용을 확인한다, **Then** 사용자가 물은 질문이
   **원문 그대로** 실려 있다.
4. **Given** LLM 인사이트 생성이 실패했다, **When** 리포트를 연다, **Then** 문장만 비어 있고
   차트·표·근거는 온전하다. 리포트 생성 자체가 실패하지 않는다.
5. **Given** 리포트에 실린 조회, **When** 리포트를 만든다, **Then** **SQL 을 다시 실행하지
   않는다** — 화면에 보인 그 결과가 그대로 실린다.
6. **Given** 리포트 파일, **When** 내용을 검사한다, **Then** SQL·호스트·계정·비밀번호가
   어디에도 없다.

### User Story 3 - 리포트를 PDF 로 만든다 (Priority: P2)

사용자가 리포트를 PDF 로 받아 메일에 첨부한다.

**Why this priority**: MD 만으로도 US2 는 성립한다. 다만 현업 유통 포맷은 PDF 이므로, 없으면
"개발자용" 인상이 남는다. P1 이 아닌 이유는 실행 환경 의존성이 있기 때문이다 (AD-4).

**Independent Test**: 스튜디오 화면에서 리포트를 열고 내보내기를 누르면 차트가 이미지로 박힌
PDF 가 만들어진다.

**Acceptance Scenarios**:

1. **Given** 생성된 리포트, **When** 스튜디오에서 PDF 내보내기를 한다, **Then** 차트가
   **이미지/벡터로 포함된** PDF 가 나온다. 빈 사각형이나 "차트 로딩 중"이 아니다.
2. **Given** PDF, **When** 한글이 포함된 리포트를 연다, **Then** 한글이 깨지지 않는다.
3. **Given** 스튜디오 프론트엔드가 없는 환경(단독 스킬 사용, 헤드리스), **When** 리포트를
   요청한다, **Then** MD 가 생성되고 **PDF 를 만들 수 없는 이유를 밝힌다.** 조용히 빠뜨리지
   않는다.

### User Story 4 - 차트가 마음에 안 들면 바꾼다 (Priority: P3)

자동으로 뜬 막대 그래프를 사용자가 파이로 바꾼다. 세션 안에서만 유지된다.

**Why this priority**: 결정적 규칙은 대부분 맞지만 항상 맞지는 않는다. 다만 없어도 P1·P2 는
성립하고, **저장·공유는 Enterprise 영역**이므로 여기서는 세션 한정이다.

**Independent Test**: 차트 타입을 바꾸고 같은 메시지를 다시 보면 바뀐 상태가 유지되며, 새
세션에서는 규칙이 정한 기본값으로 돌아온다.

**Acceptance Scenarios**:

1. **Given** 자동 렌더된 차트, **When** 사용자가 다른 타입을 고른다, **Then** 즉시 다시 그려진다.
2. **Given** 타입을 바꿨다, **When** 리포트를 만든다, **Then** 리포트에도 바꾼 타입이 실린다.
3. **Given** 타입을 바꿨다, **When** 새 세션을 연다, **Then** 규칙이 정한 기본 타입으로 돌아온다
   (저장하지 않는다).

### Edge Cases

- **결과가 30행으로 잘린 채 에이전트만 보고 있다** — 차트를 에이전트 출력에서 만들면 500행짜리
  시계열이 30점짜리 그래프가 된다. **가장 조용하고 가장 위험한 실패다.** AD-1 이 이것을 막는
  이유다.
- **`truncated` 가 false 인데 실제로 잘렸다** — CR-3 의 미탐. behavior 상한 200 에 걸린 경우가
  정확히 이 상황이고, 기본 설정에서 발생한다. 선행 수정 없이 차트를 붙이면 **틀린 그래프가
  틀린 줄 모르고 나간다.**
- **자연어 폴백 결과에 잘림 정보가 아예 없다** — `run_react_nl()` 반환에 `truncated` 키가
  없다(CR-3). 없는 것을 false 로 읽지 말고 **"알 수 없음"** 으로 다뤄야 하며, 알 수 없으면
  시계열은 그리지 않는다.
- **`entity_fetch` 결과에 `columns` 가 없다** — 키가 컬럼명이 아니라 온톨로지 property 명이다
  (`tools.py:1774-1784`). 정규화하지 않으면 카탈로그 타입 조회가 전부 빗나간다.
- **`COUNT(*)` 같은 파생 컬럼은 어느 테이블에도 없다** — 카탈로그 조회가 실패한다. 값 기반
  추론으로 내려가야 하고, 그 사실이 `type_source: "inferred"` 로 남아야 한다.
- **행 1건 · 컬럼 1개** — 대시보드에서 가장 흔한 형태(KPI)인데 규칙이 없으면 막대 하나짜리
  차트가 나온다. R1 이 이것을 잡는다.
- **모든 수치 컬럼이 식별자다** (주문번호·사번만 있는 결과) — 합계·평균이 무의미하다. G6 로 막는다.
- **범주 카디널리티가 행 수와 같다** (모든 값이 유일) — 막대 N개는 표와 같고 표보다 못하다.
  R8/R13 으로 표에 떨어진다.
- **한글 컬럼명·한글 값** — 전략 1 이 만든 클래스는 한글 식별자를 보존한다(constitution —
  *"`가-힣` 를 보존한다"*). 차트 축 라벨·범례·PDF 폰트가 전부 이것을 견뎌야 한다.
- **리포트를 만드는 사이에 소스 데이터가 바뀐다** — SQL 을 다시 돌리면 리포트의 차트와 본문이
  어긋난다. AD-3 의 결과 저장소가 이것을 막는다.
- **답변 스킬이 "파일을 만들지 않는다"고 되어 있다** (CR-9) — 스킬을 고치지 않고 도구만 추가하면
  에이전트는 그 도구를 쓰지 않는다. 도구 추가와 스킬 수정은 **한 변경 단위**여야 한다.
- **단독 스킬 사용자(005)에게는 프론트엔드가 없다** — `chart_ready` 이벤트를 받을 곳이 없다.
  차트는 안 보이고 MD 리포트만 나온다. 이 차이를 스킬 본문이 밝혀야 한다.
- **마크다운 렌더에 sanitize 가 없다** (CR-11) — 리포트 본문에 DB 에서 온 문자열이 들어가고,
  그 값에 `<script>` 가 있으면 그대로 실행된다. 지금은 소비처가 채팅 하나뿐이라 노출이 좁지만
  리포트 미리보기가 늘리게 된다.
- **`GET /api/download` 가 무조건 octet-stream** (CR-5) — HTML 리포트가 브라우저에서 열리지 않고
  내려받힌다.

## Requirements *(mandatory)*

### Functional Requirements — 선행 수정 (차트 이전에 해야 한다)

- **FR-001**: 실행 서비스가 이미 보고하는 잘림 신호(`truncated`, `returned_row_count`,
  `max_rows_cap`)를 **읽어서 전달**해야 한다. 자체 추정으로 대체하지 않는다.
  ↳ 현재: `neo4j-text2sql/app/routers/direct_sql.py:69-80` 이 주는데 `datasource_exec.py:612-615`
  가 읽지 않고 `:625` 에서 추정한다
- **FR-002**: 잘림 판정은 **behavior 별 상한에 걸린 경우도** 잘림으로 보고해야 한다. 전역 상한
  하나만 비교하면 기본 설정(behavior 200 < 전역 500)에서 미탐이 난다.
  ↳ `datasource_api.py:242`, `session_store.py:457`, `datasource_exec.py:625`
- **FR-003**: 자연어 폴백 경로도 잘림 여부를 보고해야 한다. 보고할 수 없으면 **"알 수 없음"**
  으로 명시하고, false 로 단정하지 않는다.
  ↳ `datasource_exec.py:729-740` 에 `truncated` 키 부재
- **FR-004**: 잘림의 **원인**(엔진 / behavior 상한 / 전역 상한)이 결과에 실려야 한다. 원인 없이는
  사용자가 무엇을 올려야 더 볼 수 있는지 알 수 없다.

### Functional Requirements — 결과 정규화와 보관

- **FR-010**: 도구마다 다른 결과 형태(CR-4 의 네 가지)를 **한 곳에서** 하나의 형태로 정규화해야
  한다. 호출부마다 분기하지 않는다.
  ↳ constitution 원칙 III 의 같은 논리 — 정규화는 서비스별로 한 곳
- **FR-011**: 조회 결과는 **에이전트용으로 잘라내기 전에** 전체가 보관되어야 하고, 참조 식별자
  (`result_id`)로 다시 꺼낼 수 있어야 한다.
  ↳ 잘라내기 지점 `tools.py:1645, 1786, 1851`
- **FR-012**: 도구 반환값에 `result_id` 가 실려야 한다. 에이전트가 리포트를 만들 때 **결과를
  다시 조회하지 않고** 참조로 지목할 수 있어야 한다.
- **FR-013**: 보관된 결과는 세션 수명을 넘기지 않아야 하고, 개수·크기 상한이 있어야 한다.
  무한히 쌓이면 로컬 실행 환경의 메모리를 잠식한다 (전략 §4-1 실측이 여유가 없다고 말한다).
- **FR-014**: 보관된 결과의 SQL 은 **어떤 외부 payload 에도 나타나지 않아야** 한다.
  ↳ constitution 원칙 V · 001 FR-021·022

### Functional Requirements — 컬럼 타입 판정

- **FR-020**: 각 컬럼의 역할(temporal / numeric / categorical / identifier / unknown)이
  **결정적으로** 판정되어야 한다. 같은 결과는 항상 같은 역할을 낸다.
- **FR-021**: 타입 출처 우선순위는 **바인딩 `column_map` → 카탈로그 → 값 기반 추론** 이어야 한다.
  ↳ `schema_ontology.py:270-279` · `datafabric_client.py:133-160`
- **FR-022**: SQL 타입 → 온톨로지 타입 매핑은 **기존 구현을 재사용**해야 한다. 두 번째 매핑표를
  만들지 않는다.
  ↳ `schema_ontology.py:51-66` (`map_sql_type`)
- **FR-023**: 카탈로그를 읽을 때 `type` / `dtype` 두 표기를 모두 받아야 한다. 이미 흡수 지점이
  있으므로 **그 지점을 통해서만** 읽는다.
  ↳ constitution 원칙 III · `datafabric_client.py:133-160`
- **FR-024**: 식별자 컬럼은 수치여도 **측정값으로 쓰이지 않아야** 한다. 판정 근거는 `key_columns`,
  `column_map[].reference`, 이름 접미사다.
  ↳ `schema_ontology.py:40, 276`
- **FR-025**: 타입이 무엇을 근거로 정해졌는지(`type_source`)가 남아야 한다. 이상한 차트의 원인이
  카탈로그인지 추론 규칙인지 구분할 수 있어야 한다.

### Functional Requirements — 차트 추천 (결정적)

- **FR-030**: 차트 타입은 **LLM 을 호출하지 않고** 결정되어야 한다. 같은 결과는 항상 같은 차트를
  낸다.
  ↳ 전략 §5 · constitution — *"테이블 구조 → 온톨로지 경로는 결정적이다"* 와 같은 원칙
- **FR-031**: 규칙표(§차트 추천 규칙 3단계)가 위에서부터 평가되고 **첫 번째로 맞는 규칙 하나만**
  적용되어야 한다.
- **FR-032**: **어떤 규칙에도 걸리지 않으면 표만 보여준다.** 차트를 억지로 만들지 않는다.
- **FR-033**: 가드 G1~G6 가 규칙 평가보다 **먼저** 적용되어야 한다.
- **FR-034**: 결과가 잘렸으면 차트에 그 사실이 **함께 표시**되어야 한다.
  ↳ 001 FR-029
- **FR-035**: 잘린 결과에 대해 **시계열 차트를 그리지 않아야** 한다. 잘린 시계열은 추세를
  왜곡한다.
- **FR-036**: 차트 계층은 **재집계하지 않아야** 한다. 집계가 필요한 규칙은 적용되지 않고 표로
  폴백한다.
  ↳ 001 FR-028 — *"숫자는 조회 결과를 인용하고 직접 계산하지 않는다"*
- **FR-037**: 어떤 규칙이 왜 발동했는지가 **사용자에게 보이는 한 문장**으로 제시되어야 한다.
- **FR-038**: 차트 계산은 **에이전트 도구 계층**에 두어 두 백엔드가 같은 구현을 쓰게 해야 한다.
  ↳ constitution — *"도구를 다시 구현하지 않는다"* · `agent_bridge_mcp/server.py:44-45`

### Functional Requirements — 차트 표시

- **FR-040**: 차트는 조회 결과가 나오면 **자동으로** 렌더되어야 한다. 에이전트의 추가 도구 호출을
  요구하지 않는다.
- **FR-041**: 차트 데이터는 **새 SSE 이벤트**로 전달되어야 한다. `datasource_update` 의 계약
  (*"never rows, never SQL"*)을 넓히지 않는다.
  ↳ `service.py:920-940`
- **FR-042**: 프론트로 가는 차트 payload 에 **SQL·접속정보가 없어야** 한다.
- **FR-043**: 차트가 실패해도 **답변은 정상적으로 표시**되어야 한다. 시각화는 부가물이지 답변의
  전제가 아니다.
- **FR-044**: 사용자가 차트 타입을 **세션 안에서** 바꿀 수 있어야 한다. 저장·공유는 하지 않는다.
- **FR-045**: 시각화 라이브러리는 로컬 번들이어야 하고 **외부 네트워크를 호출하지 않아야** 한다.
  ↳ 전략 §4-1 카피 전략 — *"클라우드 전송 없음"*

### Functional Requirements — 리포트 생성

- **FR-050**: 리포트 생성은 **에이전트 도구**로 제공되어야 한다. 무엇을 담을지는 대화 맥락에만
  있다.
- **FR-051**: 그 도구는 **`_ANSWER_MODE_TOOLS` 한 곳에만** 추가되어야 한다. 내장 경로와 MCP 표면이
  정확히 같아야 한다.
  ↳ constitution — *"모드별 권한을 넓히지 않는다"* · `service.py:171-182` · `server.py:30-35`
- **FR-052**: 그 도구는 **임의 코드 실행이 아니어야** 한다. `execute` 를 answer 모드에 올리지
  않는다. 인자는 결과 참조와 텍스트뿐이고 경로·파일명은 도구가 정한다.
  ↳ `sandbox_tools.py:10` — *"DEV-ONLY: there is no isolation"*
- **FR-053**: 리포트는 **결과 참조로** 만들어야 한다. SQL 을 다시 실행하지 않는다.
- **FR-054**: 리포트에 실리는 질문은 **사용자 원문 그대로**여야 한다.
  ↳ 005 FR-057 과 같은 원칙
- **FR-055**: 각 섹션은 근거(데이터소스·스키마·테이블·행 수·잘림 여부)를 함께 실어야 한다.
  ↳ 001 FR-028
- **FR-056**: LLM 은 **인사이트 문장에만** 쓰여야 한다. 차트 타입·표·수치·근거는 결정적으로
  채워진다.
- **FR-057**: 인사이트 생성이 실패해도 **리포트는 생성되어야** 한다. 문장만 비고 나머지는 온전하다.
- **FR-058**: 리포트 파일에 SQL·접속정보가 **없어야** 한다.
- **FR-059**: 리포트 생성을 지시하는 문장은 **`SKILL.md` 에 있어야** 한다. 백엔드가 파이썬으로
  조립하지 않는다. 특히 `skills/ontology-answer/SKILL.md:55` 의 *"파일을 만들지 않습니다"* 는
  같은 변경 단위에서 수정되어야 한다.
  ↳ constitution — *"지시문과 값을 섞지 않는다"* · 005 FR-010·FR-015

| 가드 | 규칙 평가 이전에 차트를 막는 조건 (실패·0건·잘린 시계열 등) |
| ChartSpec | 프론트로 건너가는 렌더 지시. SQL 을 담지 않는다 |
| 리포트 | 섹션의 나열. 각 섹션 = 질문 + 차트 + 표 + 인사이트 + 근거 |
| 인사이트 문장 | 리포트에서 **유일하게 LLM 이 쓰는 부분** |

## Assumptions

- 조회 결과가 도달하는 방법(behavior / 자연어 폴백 / entity_fetch)은 001 이 이미 정한 그대로이며
  이 스펙은 **바꾸지 않는다.** 결과의 *표현*만 다룬다.
- 시각화 라이브러리는 **Apache ECharts** 다. 전략 §5 의 확정 결정이며 이 스펙에서 재논의하지
  않는다. Superset 은 로컬에 넣지 않는다.
- 행 상한 500 은 MindsDB 실측에서 나온 값이고 바꾸지 않는다 (constitution 원칙 VI). 차트는 그
  상한 안에서 성립해야 한다.
- 결과 저장소는 **세션 수명**을 넘지 않는다. 대시보드로 저장하는 것은 Enterprise 다.
- PDF 생성은 브라우저(오늘은 스튜디오 프론트, 나중에 Electron)가 담당한다. 백엔드에 PDF 엔진을
  넣지 않는다는 것이 이 스펙의 전제다.
- `libreoffice-calc` 는 **없는 것으로 취급한다.** Writer 가용성이 미확인이고, 호출 코드가 0건이며,
  원래 소비자 파일(`recalc.py`)도 저장소에 없다.
- 답변 스킬이 리포트 생성 도구를 쓰도록 `SKILL.md` 를 수정한다. 방법론의 나머지 부분은 바꾸지
  않는다 (005 의 같은 전제).
- 이 기능은 **답변 모드**를 주 대상으로 한다. 빌드 모드의 검증 리포트(`ontology_build_report`)는
  별개이며 이 스펙이 바꾸지 않는다.

유료."* 아래는 전부 여러 사람·여러 머신을 엮는다.

  *"OSS 에는 넣지 않는다"* 고 적었다.

- **차트에서의 드릴다운·크로스필터.** 상호작용은 저장된 대시보드와 함께 오는 것이 자연스럽다.
- **여러 조회 결과를 하나의 차트로 합치기.** 조인은 SQL 의 일이다 (001 의 같은 원칙).
- **백엔드 차트 렌더링**(matplotlib/plotly/ECharts SSR). 의존성이 전략 §4-1 의 메모리 예산과
  충돌한다.
- **`ontology_build_report` 의 개편.** 빌드 검증 리포트는 별개 경로다.
- **마크다운 sanitize 도입**(CR-11). 이 스펙이 노출을 넓히는 것은 사실이므로 **리스크로 기록**하되,
  수정은 별도 변경 단위로 다룬다.
- **Electron 패키징**(전략 §6 작업 7). PDF 경로가 그것에 의존하지만, 이 스펙은 Electron 없이도
  성립하는 브라우저 인쇄 경로를 v1 로 잡는다.
